## 0. 시스템 요약 (이 문서만 읽어도 되도록)

- **무엇**: 차트 기반 스크리너 + 서버사이드 자동 모의투자(시드 1억). 서버 없음 —
  전부 GitHub Actions(빌드당 새 VM) + Pages(정적 호스팅) + 텔레그램(알림).
- **주기**: 한국장 15분(kr) / 미국장 15분(top) / 마감후 풀빌드 1회. 매매·알림은
  빌드 안에서 완결, Pages 배포는 표시용일 뿐.
- **제약**: 비용 0원, GitHub 중심 유지, 운영자는 비개발자 1인(하루 5분).
- **지난 검토의 핵심 지적**: ① 계좌 상태가 휘발성 actions/cache에만 존재
  ② 손절 집행이 15분 폴링 빌드에 종속 ③ 기계용 feed가 사람용 Pages와 결합
  ④ 스케줄러·알림·감시가 전부 GitHub 단일 장애점.

## 2. 구현 상세

### 2.1 계좌 영구 백업 — state 브랜치 (§2)
- 매 빌드 종료 시 `state` 브랜치에 커밋(`[skip ci]`): ① 계좌 스냅샷
  `state/autopaper.snapshot.json` ② 월별 append-only 원장 `state/ledger/YYYY-MM.jsonl`
  ③ 기계용 feed `feed/{signals.latest,autopaper.public,heartbeat}.json`.
- 복구 체인 확정: **본파일 → .bak → state 브랜치 스냅샷(CI에서만) → 새 계좌**.
- 백업 실패는 빌드를 죽이지 않음(`set +e` 래핑 + `::warning`) — 백업이 매매를
  방해하면 본말전도라서.
- **실가동 증거**: 7/7 12:23:44 KST 첫 스냅샷 생성, 이후 매 빌드 갱신 확인
  (heartbeat에 run_id·트리거 종류 기록).

### 2.2 기계용 feed 분리 + advisor 신선도 가드 (§4)
- advisor(매수 제안 봇)가 raw.githubusercontent의 state 피드를 1순위, Pages를
  폴백으로 읽는 체인. 장중 신호가 25분+ 낡으면 **제안을 내보내지 않고** 하루
  1회 '신호 낡음' 경보만 발송 — 낡은 가격 기반 제안 차단.
- 알림 예산 `DAILY_ALERT_BUDGET=40`/일 — 폭주 시 자동 차단.
- 발송 직전 장시간 재확인(ET 타임존 기준) — 장외 발송 방지.

### 2.3 매도 전용 파수꾼 (§3) — 코드 완성, 미가동
- `bot/sentinel.py`: 20초 폴링으로 보유 종목의 손절선만 감시·집행하는 상주
  프로세스 설계. **매수 경로가 소스에 존재하지 않음**(테스트가 소스 grep으로
  영구 검증). 하드 스탑 1% 버퍼, 멱등키(`{code}:{stop}:{date}`)로 중복 주문
  방지, 피드 30분+ 낡으면 보호 모드.
- 기본 dry-run(페이퍼 브로커). 실거래는 `SENTINEL_LIVE=1` + 토스 어댑터 구현
  시에만 — 키는 env 전용, 코드/로그에 노출 경로 없음.
- 검토 권고대로 "실거래 전 필수 3종"(손절 분리/상태 백업/외부 감시자) 중
  1번을 미리 완성해둔 것.

### 2.4 보안·공회전 가드 (§6)
- fine-grained PAT: Actions RW · 1개 repo · 90일 만료 — 유출 시 피해 상한을
  "빌드 강제 실행"으로 축소.
- daily.yml 앞단 **guard job**: 외부 dispatch(top)인데 라이브가 신선(<40분)이면
  no-op 종료, `full`은 `confirm=FULL` 없이 거부. 가드 자체가 죽으면 fail-open
  (감시가 매매를 막지 않도록).

### 2.5 외부 스케줄러 (§1 순서 변경) — **가동 중**
- cron-job.org가 15분마다 `workflow_dispatch` POST (사용자가 직접 설정 완료,
  테스트 204 확인). GitHub 크론과 이중화 — 어느 한쪽이 죽어도 빌드가 돈다.
- CF Worker(응답 검증·조건부 킥)는 실거래 결정 시 업그레이드 예정.

### 2.6 기타 (지난 검토 이전 조치 포함, 맥락용)
- GitHub 크론 오프피크 이동(:04/:19/:34/:49) — 정각 피크 드랍 대응.
- 워치독 장세 인지 임계(장중 45분/마감후 150분/장외 생략) + 정체 시 자동 재실행.
- Pages 배포 실패 90초 백오프 재시도 + 실패 텔레그램. 빌드 실패도 텔레그램.
- 수동 탈출구: 커밋 제목 `[update-top]` = 강제 신선 빌드.

## 3. 검토 이후 실측 사건 3건 — 권고의 실증

### 사건 A: GitHub 이벤트 전면 미생성 (7/7 09:05~12:08 KST)
- **증상**: push·schedule 이벤트가 **런을 아예 생성하지 않음** 3시간. 워크플로
  active, 스키마 정상, GitHub 공식 status는 operational. 원인 미상(플랫폼).
- **생존자**: API `workflow_dispatch`만 런 생성 — **사용자의 cron-job 테스트
  호출이 3시간 만의 첫 빌드를 만들었다.** "외부 스케줄러가 유일한 독립 층"
  이라는 지난 검토 §1의 주장이 도입 당일 실증됨.
- **잔존 이슈**: schedule·dispatch는 회복됐지만 **push 이벤트는 아직도 런을
  안 만든다** (기본 브랜치 머지가 재배포를 트리거하지 않음). 크론이 1분 뒤
  새 커밋을 집어가서 실피해는 0이지만, 원인 불명 상태로 지속 중. ← 질문 3

### 사건 B: 규칙 위반 오탐 (7/7 12:21 KST)
- 🚨 "하루 신규 진입 4건 > 상한 3" 경보 발화. 조사 결과 **회계 버그**: 전일
  지정가 주문이 당일 체결되면 주문일 +1, 체결일 +1로 이중 카운트. 실제 진입
  결정은 상한 이내(규칙 위반 없음).
- 수정: 카운트를 '진입 결정 시점'으로 단일화(체결은 불집계) + 이 시나리오를
  영구 회귀 테스트로 고정. 당일 수정 배포.
- **의미**: 사후 감사→텔레그램 경보 체인이 실전에서 처음 발화해 끝까지 도달
  — 오탐이었지만 감지 체계 자체는 설계대로 작동.

### 사건 C: 테스트 격리 오염 (state 브랜치의 부작용)
- state 브랜치가 생기자 로컬 테스트의 복구 체인 3단계가 **운영 계좌를 끌어와**
  전 스위트가 오염됨. 복구 경로에 `GITHUB_ACTIONS=true` 가드 추가로 해결.
- 교훈: 복구 경로를 강화할수록 "복구가 일어나면 안 되는 환경"의 명시가 필요.

## 4. 현재 방어 계층 (이행 후 스택)

```
스케줄 3중화: GitHub cron(오프피크) + cron-job.org(15분) + 워치독 자가치유
                + 수동 탈출구([update-top] 푸시)
상태 3중화:   원자적 본파일 + .bak + state 브랜치(스냅샷·원장·feed)
감지:         빌드/배포 실패 텔레그램 · 규칙 사후감사 경보(실증됨) ·
              워치독 정체 경보 · advisor 신호낡음 경보 · 알림 예산
실거래 대비:  sell-only sentinel 완성(dry-run) · PAT 최소권한 · 공회전 가드
남은 단일점:  텔레그램(알림 채널 1개) · GitHub 전면 장애 시 매매 공백
              (계좌는 안전) · 운영자 1인
```

## 5. 재평가 질문 (이번에 답해줬으면 하는 것)

1. **이행 품질**: 위 §2 구현들에서 빠뜨린 디테일이나 잘못 구현한 부분이 보이나?
   특히 state 브랜치 백업(2.1)과 guard job(2.4)의 실패 모드.
2. **우선순위 재조정**: 이행 후 남은 약점(§4의 '남은 단일점') 중 다음 1개를
   고른다면? 근거는 "모의투자 단계 + 운영자 하루 5분" 제약 하에서.
3. **사건 A의 push 이벤트 미복구**: 기본 브랜치 push가 런을 안 만드는 상태가
   지속되는 원인 가설과, 크론 픽업 외에 추가로 걸어둘 방어가 있나?
   (참고: schedule·dispatch는 정상, 워크플로 파일 유효, status 페이지 정상)
4. **실거래 전 필수 체크리스트**: 지난 검토의 3종(손절 분리·상태 백업·외부
   감시)에서 추가/변경할 것이 있나? sentinel의 멱등키·보호모드 설계(2.3)에
   구멍이 있나?
5. **과설계 점검**: 반대로, 모의투자 단계에 이미 과한 부분이 있으면 지적해달라.
   우리 원칙은 "외부 계정·관리 대상 최소화"다.

— 이상. 구체적 실패 시나리오와 함께 지적해주면 바로 반영한다.
