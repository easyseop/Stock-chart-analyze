## A부 — 초기 운영기 사건 (6/25 ~ 7/5)

### A1. 캐시 경합 — 즉석조회 종목 소실 (6/25, 심각도: 중간)

- **증상**: 사용자가 사이트에서 즉석조회로 추가한 종목이 다음 빌드에서 사라짐.
- **원인**: 상태 저장이 `actions/cache` 단일 의존 + 동시 실행 워크플로(daily와 lookup)
  간 캐시 경합/리셋 — 나중에 저장한 쪽이 이기면서 다른 쪽 수집분 유실.
- **조치**: 즉석조회 목록을 별도 영구 보존 경로로 분리.
- **교훈**: actions/cache는 "여러 쓰기 주체"에 안전하지 않음 — 이후에도 반복되는 주제.

### A2. 중복 실행·배포 충돌 (6/27, 심각도: 낮음)

- **증상**: 여러 브랜치 푸시가 각각 빌드를 트리거 → 동시 Pages 배포 충돌.
- **조치**: push 트리거를 기본 브랜치 하나로 한정 + `concurrency: pages` 그룹으로
  배포 직렬화.

### A3. 갱신 주기 확장기의 수동 운영 (6/28~29, 심각도: 낮음)

- **내용**: 한국주 302종목 백필을 위해 push 트리거 MODE를 일시적으로 full로 바꿨다
  원복하는 수동 운영 2회. 장중 주기도 30분→15분으로 조정(데이터원 차단 없는 안전
  최대치 실측).
- **교훈**: "일회성 수동 모드 전환"은 원복을 잊으면 사고가 되는 패턴 — 이후
  workflow_dispatch 입력과 커밋 마커로 대체됨.

### A4. Pages 배포 타임아웃 — 큐 정체 (7/2, 심각도: 중간)

- **증상**: 15분마다 배포하니 Pages 배포 큐가 정체 → 기본 10분 타임아웃 초과로
  배포 실패 반복.
- **조치**: 타임아웃 10→20분. **Pages 불안정의 첫 관측** — 7/3(재시도 추가),
  7/6(연속 실패→90초 백오프)으로 이어지는 만성 주제.

### A5. 반영 지연 — 빌드가 느려서 사실상 주기 붕괴 (7/3, 심각도: 높음)

- **증상**: 상세페이지 ~900MB(5,400종목)를 매 빌드 전체 재렌더 → 빌드가 길어져
  15분 주기가 사실상 지켜지지 않고 사이트 반영이 만성 지연.
- **원인**: 증분 렌더 부재(구조 문제). "크론은 돌았는데 결과가 늦는" 유형.
- **조치**: BUILD_SHA 기반 증분 렌더(바뀐 종목만) + **1세대 신선도 워치독 신설**
  (에폭 data-ts 기반, 정체 시 자동 재실행).

### A6. 주말 가짜 체결 (7/5~6, 심각도: 높음 — 신뢰성)

- **증상**: 주말(장 닫힘)에 코드 푸시로 돌던 빌드가 **금요일 종가로 자동매매 진입**
  — 사용자가 "주말 진입은 신뢰성이 떨어진다" 지적.
- **원인**: 자동매매가 "빌드가 돌면 판정"하는 구조였고 장중 여부를 확인하지 않음.
  크론은 평일 전용이지만 **푸시 빌드는 요일을 가리지 않음**을 간과.
- **조치**: `market_open` 게이트(장중에만 진입/청산) + 상태 VERSION 리셋으로 주말
  체결 무효화. 이후 서머타임 정확 반영(7/6)으로 발전.

### A7. daily.yml 만성 실패 — 스모크체크 마커 (7/5 리디자인 ~ 7/6 발견, 심각도: 중간)

- **증상**: 홈 UI 리디자인 후 배포 후 검증(스모크체크)이 옛 문구를 grep → **모든
  빌드가 빨간불**. 실제 배포는 되고 있었지만 "전부 실패"로 표시돼 진짜 실패와
  구분 불가(늑대소년 상태).
- **탐지 경로**: 월요일 아침 "자동매매 0건" 원인 조사 중 발견 — 역시 무음/오표시.
- **조치**: 스모크 마커를 리디자인 후 안정 마커로 교체.
- **교훈**: 감시 코드도 UI 변경과 함께 깨진다 — 감시의 회귀 테스트 필요.

### A8. 알림봇 크론 부분 드랍 + 폭주 (7/6 낮, 심각도: 중간)

- **증상**: advisor(매시 2회 예정)가 그날 **13:36 단 1회만 실행** — 그 한 번에
  밀린 신호 55건을 폭주 발송(장 닫힌 미국주 제안 포함).
- **원인**: ① 크론 드랍(그날 저녁 대량 드랍의 전조) ② 장중 필터·회당 상한 부재.
- **조치**: 장중 시장만 + 회당 상한(8/6) → 이후 일일 총량 40건 서킷브레이커,

### A9. 수동 개입 경로 차단 발견 — dispatch 403 (7/6, 심각도: 낮음)

  후 1시간+ 자동매매 조용히 정지.

## 종합 — 패턴과 교훈

1. **13건 중 매매 로직 자체의 오류는 A6(주말 체결) 하나** — 나머지 전부가 인프라의

2. **반복 주제 3개**: ① GitHub 스케줄러 best-effort(A8→B1) ② Pages 불안정
   (A4→7/3→B2, 3회) ③ actions/cache 단일 저장의 취약성(A1, 그리고 계좌 상태가
   지금도 같은 구조).
3. **탐지 경로가 문제였다**: 주요 사건 대부분을 시스템이 아니라 **사용자가 먼저
   발견**(A6 주말 체결, A7 0건 조사, B1 알림 부재, B5 화면). 7/6 밤 이후 모든 실패
   경로에 텔레그램 자동 경보를 붙인 이유.
4. **감시 코드 자체의 회귀**가 두 번(A7 스모크 마커, B4 임계) — 감시도 코드다.
5. **남은 구조적 약점**: ① 감시자(워치독)도 같은 GitHub 크론(상관 장애, B1에서 실측)
   ② 계좌 상태 actions/cache 단일 저장(7일 미사용 소멸·임의 evict) ③ 경보 채널
   텔레그램 단일 ④ 15분 폴링+best-effort 스케줄러로 실계좌 손절 관리 가능한지 미검증.
