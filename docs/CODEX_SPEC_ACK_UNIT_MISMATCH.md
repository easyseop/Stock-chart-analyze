## C1 (P1) — `hldg_before`가 SELL에서만 '매도가능'을 담는다

### 증거

기록 측 (`bot/sentinel.py:192-221`, `place_sell`):

```python
fresh = (kis.sellable_holdings("KR") if market == "KR"
         else kis.sellable_holdings("US", excg=excg))
fresh_qty = max(0, int(fresh.get(str(code).upper(), 0)))
safe_qty  = min(max(0, int(qty)), fresh_qty)
...
r = kis_orders.place_sell(..., hldg_before=fresh_qty, ...)   # ← 매도가능
```

소비 측 (`bot/kis_boot.py:428-446` → `bot/kis_reconcile.py:734-739`):

```python
h = kis.holdings("US", excg=ex)      # ← 총보유
hmaps["US"] = merged
...
now_qty = int(hmap.get(S, 0))
delta = (now_qty - before) if side == "BUY" else (before - now_qty)
```

`bot/kis.py:868-874`의 `sellable_holdings` 독스트링이 이 함정을 이미 적어 두었다:

> 총보유(hldg_qty/ovrs_cblc_qty)는 **미체결 매도**·결제 상태 때문에 실제
> 주문가능수량과 다를 수 있다.

두 값이 어긋나는 조건이 하필 *미체결 매도가 있을 때*인데, 우리 청산은
`1절 종결 → 익절 절반`으로 2단이라 매도가 겹치는 것이 **정상 경로**다.
이 오탐은 우연이 아니라 구조적으로 반복된다.

BUY 경로는 문제없다 — `bot/kis_buyloop.py:279`가
`positions_detail(...)["qty"]`(총보유)를 쓰고 있어 소비 측과 단위가 같다.
**SELL 경로만** 어긋나 있다.

### 영향

| 실제 상황 | 참 delta | 계산된 delta (R=예약수량) | 결과 |
|---|---|---|---|
| 미체결 | 0 | `-R` | **오탐 동결** ← 이번 사고 |
| 정상 full-fill | Q | `Q-R` | 자동확정 실패 → 대사 지연 |
| 실제로 Q+R 감소(진짜 이상) | Q+R | `Q` | **이상을 정상 체결로 자동확정** ⚠ |

마지막 행이 위험 방향이다. 지금은 오탐(보수적 실패)만 관측됐지만, 같은 버그가
반대로도 터질 수 있다.

### 요구사항

1. `hldg_before`는 **이름 그대로 총보유**를 담는다. 소비 측 3곳과 BUY 경로가
   이미 그 전제로 동작하므로, 기록 측을 맞추는 것이 최소 변경이다.
2. 매도 직전 안전 클램프(`safe_qty = min(qty, 매도가능)`)는 **지금처럼
   매도가능을 계속 쓴다.** 초과매도를 막는 건 그쪽이 맞다. 두 용도를 분리하라.
3. 추가 API 호출을 만들지 말 것. `holdings()`와 `sellable_holdings()`는 같은
   `domestic_balance()/overseas_balance()` 응답을 파싱한다 — 한 번의 응답에서
   두 map을 함께 뽑는 접근자를 만들거나, 기존 캐시를 재사용하라.
4. 총보유 조회가 실패하면 `hldg_before`를 **추측하지 말 것**. 매도가능으로
   대신 채우면 지금 버그가 그대로 재현된다. 이 집 규칙대로 `None`(실패≠부재)로
   두고, 소비 측이 이미 `before_raw is None` 분기를 갖고 있으니 그 경로를 타게
   하라 (`kis_reconcile.py:360`).
5. **매도 자체를 막지 말 것.** 총보유 조회 실패는 손절을 보류할 사유가 아니다.
   보호 핫패스는 매도가능만 있으면 주문을 낸다. 기록만 `None`이 된다.

### 반드시 있어야 할 회귀 테스트

- 총보유 11 · 매도가능 6(미체결 매도 5) 상황에서 SELL 접수 →
  원장 `hldg_before == 11`, 전송 수량 `min(요청, 6)`.
- 그 주문이 미체결일 때 `resolve_acks_by_balance` → `delta == 0` →
  **동결 없음** · 자동확정 없음(다음 사이클 재검사).
- 그 주문이 5주 full-fill → `delta == Q` → 정상 자동확정.
- 총보유 조회만 실패 → `hldg_before is None`, 매도는 정상 접수.
- 매도가능 조회 실패 → 기존대로 `rejected`(주문 안 나감).

## C2 (P1) — 동결이 대사 3경로를 전부 막아 자기잠금이 된다

### 증거

동결 게이트가 세 군데 전부에 있다:

```
bot/kis_reconcile.py:580   reconcile_unknowns        → "ownership 미armed/기보유/동결" LOW
bot/kis_reconcile.py:731   resolve_acks_by_balance   → continue
bot/kis_reconcile.py:395   resolve_acks_by_absence   → continue
```

따라서 C1이 만든 오탐 동결 이후 INGR SELL은 **어떤 경로로도 해소될 수
없다.** 23:15의 `ACK 30분 초과` 경보가 그 결과이고, 앞으로 계속 반복된다.

게다가 **동결만 풀어도 즉시 다시 얼어붙는다** — `hldg_before=6`이 그대로라
다음 사이클에 `6-11=-5`가 재현되고, 3순위로 가도
`unchanged = (6 == 11)` False → `absence-balance-contradiction` P0가 뜬다.

### 설계 의도 (이 경계를 지켜라)

동결의 목적은 "외부 개입이 의심되는 종목에서 **추론으로** 체결을 확정하지
않는 것"이다. 그런데 지금 구현은 추론과 직접 증거를 구분하지 않는다.

- **직접 증거** — ODNO가 정확히 일치하는 체결행(ccnl). 이건 브로커가 "이
  주문이 이만큼 체결됐다"고 말한 것이지, 잔고 차이에서 유추한 게 아니다.
  동결과 무관하게 **허용**해야 한다.
- **추론 증거** — 잔고 delta(2순위), 부재+잔고불변(3순위). 외부 개입이 있으면
  전제가 무너진다. 동결 시 **계속 보류**한다.

즉 `reconcile_unknowns`의 동결 게이트를 "ODNO 정확 일치 + 단일
non-terminal 주문"인 경우에 한해 통과시키고, 나머지 게이트(G1·G2·기보유
denylist)는 그대로 둔다. 2순위·3순위는 지금처럼 보류한다.

`symbol in base`(사용자 기보유 영구 denylist)는 **완화하지 말 것.** 그건
동결과 성격이 다르다.

### 추가로 필요한 것 — 막힌 주문을 사람이 푸는 길

C1을 고쳐도 **이미 ack에 갇힌 기존 주문**은 남는다. 운영자 ack를 요구하는
CLI가 필요하다. 기존 `scripts/kis_arm.py`·`bot/ownership.unfreeze(ack=...)`
규약을 따를 것:

```
python scripts/kis_ack_resolve.py --key <원장키> --plan      # 미리보기
python scripts/kis_ack_resolve.py --key <원장키> --apply --ack "<사유>"
```

- 기본 미리보기. `--apply`에 운영자 ack 문자열 필수.
- 브로커 체결조회·잔고를 **다시 읽어** 근거를 보여준 뒤 확정한다.
  근거 없이 원장만 바꾸는 경로는 만들지 말 것.
- 조회 실패면 아무것도 하지 않는다(실패≠부재).
- 결과는 감사 원장에 append.

### 반드시 있어야 할 회귀 테스트

- 동결 종목 + ODNO 일치 체결행 존재 → 확정된다.
- 동결 종목 + 잔고 delta만 존재(체결행 없음) → 확정 안 된다.
- 동결 종목 + 부재 증명 → 확정 안 된다.
- `symbol in base`(사용자 기보유)는 ODNO 체결행이 있어도 기존대로 보류.
- 동일 심볼 non-terminal 주문이 2개 이상이면 ODNO 있어도 보류(귀속 모호).

## C3 (P2) — 거절 사유가 '미상'으로만 남는다

### 증거

같은 날 두 건이 모두 사유 없이 종결됐다:

```
⚠️ 파수꾼 1절 종결(0체결+잔고 증명) — INGR 5주 · 사유 미상 · 접수 22:33
⚠️ 매수 거절 종결(0체결+잔고 증명) — OMCL 68주 · 사유 미상 · 접수 22:44
```

OMCL은 접수(ack)까지 받은 68주 매수가 11분 뒤 0체결로 사라진 건이다. 같은
세션에서 PEP 16주·NKE 3주는 1분 만에 체결 확정됐으므로 전역 차단이 아니라
**그 주문 고유의 사유**가 있었을 텐데, 우리는 그게 뭔지 모른다.

이건 안전 문제는 아니지만(fail-closed로 잘 닫혔다) **재발 방지가 불가능한
상태**다. 사유를 모르면 고칠 수도 없다.

### 요구사항

1. 주문 접수 응답(`msg_cd`/`msg1` 등 KIS가 주는 코드·메시지)을 원장 meta에
   보존하라. 이미 `ledger.py:554`에 meta 화이트리스트가 있으니 거기에 얹는다.
2. 미체결 조회(nccs)에 그 ODNO가 있을 때의 상태 필드도 마지막 관측값으로
   남겨라 — 부재 증명으로 종결할 때 "마지막으로 본 상태"를 함께 보고할 수 있게.
3. 종결 알림의 `사유 미상` 자리에 보존된 코드·메시지를 넣는다. 없으면
   `사유 미상(마지막 관측: <상태>)`처럼 **무엇까지 알았는지**를 남긴다.
4. **비밀 누출 금지** — 계좌번호·토큰이 msg에 섞여 올 수 있다. 공개 ntfy
   경로에는 기존 규칙대로 분류만 싣고, 상세는 텔레그램·`/진단`에만.

## 지켜야 할 불변식 (전 항목 공통)

1. 주문 발주 경로의 안전 클램프는 **약화 금지**. `safe_qty`는 계속
   매도가능 기준.
2. `실패 ≠ 부재` — 조회 실패는 `None`, 성공·빈 결과는 `[]`/`0`. 섞지 말 것.
3. 자동 확정은 **증거가 정확히 일치할 때만**. 애매하면 보류하고 다음 사이클.
4. 동결 해제·원장 강제 확정은 **운영자 ack 필수**. 코드가 스스로 풀지 않는다.
5. 사용자 기보유(`ownership.baseline()`) denylist는 어떤 경우에도 완화 금지.
6. kill-switch·손절 발주 경로에는 diff가 없어야 한다.
