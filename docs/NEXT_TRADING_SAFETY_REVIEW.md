# 다음 검토 요청 — KIS 주문 경합·총시드·손절 보호 전수 점검

작성일: 2026-07-24
대상 저장소: `easyseop/Stock-chart-analyze`
검토 성격: **코드 수정 전 독립 안전성 검토**

> 이전 웹 UX 검토와 별개다. 이번에는 화면이 아니라 실제 KIS 모의주문의
> `주문 접수(ACK) → 잔고 반영 → 체결 대사 → 보호선 생성` 순서가 뒤바뀌는 경우와
> A/B/총시드 한도를 집중 검토해 달라.

## 1. 검토자가 지켜야 할 범위

- 현재 단계는 KIS 모의계좌지만 실전 전환을 전제로 안전성을 평가한다.
- 코드를 고치지 말고 먼저 결함 여부와 우선순위를 독립적으로 판정한다.
- 기존 테스트 통과나 이전 리뷰의 “양호” 결론을 신뢰 근거로 삼지 말고,
  주문·잔고·체결 API 응답 순서를 의도적으로 바꾼 실패 시나리오로 확인한다.
- 시크릿, 계좌번호, 토큰, 실제 SSH 정보는 요구하거나 출력하지 않는다.
- 결과는 각 항목마다 `P0~P3 / 파일·함수 / 재현 순서 / 영향 / 최소 수정안 /
  반드시 추가할 테스트` 형식으로 작성한다.

## 2. 실제 관찰 사건

미국 장중 아래 순서가 실제 운영 로그에서 관찰됐다.

1. 전략 B의 ALK 매수 주문이 KIS에서 `ACK`(주문 접수)됐다.
2. 체결 대사와 로컬 보호 포지션 기록이 끝나기 전에 KIS 잔고에는 ALK가 먼저 보였다.
3. 파수꾼은 ALK 실보유를 발견했지만 로컬 `kis_positions`에 손절선이 아직 없어
   `손절선 불명` 경보를 냈다.
4. 같은 시점 매수 루프는 ALK를 B의 미확정 주문에서도 제외하고 B 보유에서도
   찾지 못해 B 사용량을 적게 계산했다.
5. 그 결과 직전 사이클에서 B 한도로 막혔던 SIG 주문이 다음 사이클에 접수됐다.
6. 이후 대사가 끝나 ALK와 SIG 모두 정상 포지션으로 기록됐지만, 그 사이에는
   B 예산 과소계상과 보호선 공백이 존재했다.

중요한 질문은 “결국 대사됐는가”가 아니라, **대사 전 1~2분 동안에도 신규매수 한도와
손절 보호가 보수적으로 유지됐는가**다.

## 3. 우선 확인할 결함 후보

### A. ACK 주문이 잔고에 먼저 보이면 B 예약금액에서 사라짐

- `bot/kis_buyloop.py::_broker_state`
  - in-flight BUY를 접을 때 `symbol in held`이면 건너뛴다.
  - `inflight`가 `dict[symbol]`이라 같은 종목에 여러 예약이 있으면 마지막 하나가
    앞 예약을 덮을 수 있다.
- `bot/kis_buyloop.py::_b_held_codes`
  - B 보유 판정은 체결 후 생성되는 `kis_positions` 태그에 의존한다.
- `bot/kis_buyloop.py::_partition`
  - 아직 B 태그가 없는 실보유는 사실상 A로 귀속된다.

검토 질문:

1. `ACK → 잔고 반영 → 체결 대사` 순서에서 종목과 금액이 B·총시드 예약에 끝까지
   남는가?
2. 같은 종목의 1차/2차·부분 주문 예약을 합산하는가?
3. 슬리브를 확정할 수 없는 보유는 A로 추정하지 않고 신규매수를 닫는가?

### B. 예약·보유·계획 주문을 합친 총시드 원자적 게이트 부재

현재 운영 의도는 A와 B의 합을 하나의 총시드 안에 두는 것이다. 실제 판단에서는
`확정 보유 + ACK/UNKNOWN/부분체결 + 아직 살아 있는 계획 주문 + 수수료·환율 여유분`을
동시에 예약해야 한다.

검토할 불변식:

```text
reserved_total + worst_case_new_order <= operating_total
reserved_sleeve + worst_case_new_order <= sleeve_budget
```

- `operating_total`은 총시드 전액이 아니라 환율·수수료·가격 미끄러짐용 완충액을
  제외한 금액이어야 한다.
- 작은 시드에서 위험 한도를 지키는 1주조차 살 수 없으면 1주를 강제로 사지 말고
  건너뛰어야 한다.
- `can_submit` 확인과 예약 기록이 서로 다른 프로세스에서 경합해도 한 거래처럼
  원자적으로 처리돼야 한다.

정책안도 함께 평가해 달라.

- A/B 초기 비율은 현재 의도된 30:5, 즉 약 85.7%:14.3%를 유지한다.
- 총시드의 5%를 운영 완충액으로 먼저 떼고 나머지만 A/B에 배분한다.
- 성과에 따른 배분 변경은 최소 3개월·슬리브별 종료 거래 60건 이후 월 1회,
  한 번에 ±5%p 이내로 제한한다.
- 명목금액 한도와 별도로 전체 열린 위험금액(모든 손절 도달 가정) 상한을 둔다.

### C. 계획 주문이 B 예산·보유 수를 우회할 가능성

- `bot/kis_pending.py::process`
  - 계획 주문 제출 시 `seed_krw=None`, `open_positions=None`,
    `open_cost_krw=None` 경로가 실제 B 봉투와 총시드 게이트를 우회하지 않는지 확인한다.
- 부모 주문 부분체결·잔량 미체결·취소 대기 중 2차 주문이 동시에 살아나는 경로도
  장애 주입으로 검증한다.

### D. 잔고에는 있으나 보호선 기록 전인 종목의 손절 공백

- `bot/sentinel.py::check_once`
  - KIS 실보유에는 있으나 `feed`와 `kis_positions`에 아직 손절선이 없으면 경보만 내고
    보호 대상에서는 제외한다.
- 주문 원장에는 ACK 단계부터 `stop`, `target`, `sleeve`, `pos_key`가 저장된다.

검토 질문:

1. 확정 대사 전에는 원장의 보호선을 임시 보호선으로 사용할 수 있는가?
2. 브로커 잔고 증가량과 원장 BUY를 유일하게 연결할 수 없으면 어떤 상태로
   잠그고 사용자에게 무엇을 알려야 하는가?
3. “손절선 불명”과 “주문 접수 후 대사 중”을 서로 다른 알림으로 구분해야 하는가?

### E. 부분체결된 BUY의 잔량 주문 때문에 실제 보유분 손절이 막힘

- `bot/sentinel.py::check_once`
- `bot/kis_exits.py::manage`

두 경로 모두 종목에 in-flight 주문이 하나라도 있으면 매도를 건너뛴다. BUY가
부분체결돼 실제 보유가 생겼지만 잔량 BUY가 미체결인 상태에서 가격이 손절선을
이탈하면 보호가 멈출 수 있다.

기대 동작 후보:

1. 남은 BUY 취소 요청
2. 취소/체결 상태 재조회
3. 확정 보유·매도가능수량만 손절
4. BUY 생사가 불명확하면 신규 주문은 막되, 이미 체결된 수량의 보호를 영구히
   포기하지 않는 별도 상태기계 사용

이 순서가 초과매도와 손절 누락을 동시에 막는지 반증해 달라.

### F. 매도 ACK를 체결로 오인해 절반 익절·본전 손절을 먼저 확정

- `bot/kis_exits.py::manage`
  - `state in ("ack", "filled")`를 성공으로 취급한다.
  - ACK에서 `filled=0`이어도 `half=True`로 저장하고 손절선을 본전으로 올릴 수 있다.

확인할 불변식:

- 주문 접수 알림과 체결 확정 알림은 문구·상태·회계 모두 분리한다.
- 절반 익절 완료, 손절선 본전 상향, 원가 환입은 **실제 체결수량 확인 후에만** 한다.
- 부분체결이면 실제 체결분만 반영하고 잔량 상태를 유지한다.

### G. 파수꾼 하트비트가 없는데 첫 신규매수는 허용될 가능성

- `bot/heartbeat.py::entry_allowed`
  - 하트비트가 없고 보유 포지션도 없으면 `P0`이지만 `HARD_DISABLE`은 아니어서
    신규 진입을 허용할 수 있다.

검토 질문:

- “보유가 없으니 잃을 것이 없다”가 아니라 “매수 직후부터 보호할 파수꾼이 없다”가
  맞으므로, 최근 정상 하트비트 없이는 첫 매수도 fail-closed 해야 하지 않는가?

### H. KIS 호출 제한이 프로세스와 재시도 사이에서 공유되지 않음

- `bot/kis_ratelimit.py`
  - 리미터는 프로세스 내부에서만 공유된다.
- `bot/kis.py::_get`
  - 한 번 슬롯을 얻은 뒤 최대 세 번 HTTP 요청할 수 있다.
- `bot/kis_orders.py::place_order`
  - 한 번 order 슬롯을 얻은 뒤 재시도 요청을 추가로 보낼 수 있다.
- 현재 `sentinel`, `buyloop`, `portfolio-web`이 별도 프로세스다.
- 실제 모의계좌 로그에서 `EGW00201`이 반복 관찰됐다.

검토할 설계안:

- 계좌 단위 단일 KIS 게이트웨이 또는 프로세스 간 공유 리미터
- 모든 HTTP 재시도마다 새 슬롯 획득
- 손절·취소·대사를 최우선, 잔고·차트·후보 조회는 후순위
- 보유 현재가와 체결 통지는 WebSocket을 우선 사용하고 REST는 복구·대사에 사용
- 웹은 계속 공유 캐시만 읽어 주문 경로의 KIS 호출을 늘리지 않음

### I. 주문 원장의 내구성과 원자성

- `bot/ledger.py`
  - append-only JSONL이지만 쓰기 후 `fsync`와 프로세스 간 잠금이 없다.
  - 손상된 JSON 줄을 조용히 건너뛴다.
  - `can_submit` 확인과 `record_submit`이 하나의 원자적 거래가 아니다.

검토 질문:

- 크래시, 디스크 부족, 두 프로세스 동시 주문에서 중복·예약 소실이 가능한가?
- SQLite WAL + 단일 writer/transaction으로 바꾸는 것이 최소 안전선인가?
- 원장 손상을 발견하면 조용히 계속하지 않고 신규 주문을 닫아야 하는가?

### J. 실주문 게이트와 브로커 조회 실패 폴백

- `bot/sentinel.py::_KisBroker.place_sell`
  - KIS 경로가 `SENTINEL_LIVE`를 직접 확인하지 않아 화면의 “dry-run” 표시와 실제
    전송 게이트가 일치하는지 검토가 필요하다.
- `bot/sentinel.py::check_once`
  - 브로커 잔고 조회 실패 시 공개/paper feed 보유로 폴백한다.

검토할 불변식:

- `SENTINEL_LIVE != 1`이면 어떤 KIS 주문 함수도 호출되지 않는다.
- KIS 실행 모드에서 브로커 잔고 조회 실패 시 마지막 정상 브로커 스냅샷의 나이와
  신뢰도를 사용하고, 공개 paper feed만으로 실제 매도를 결정하지 않는다.

### K. 성과·지수 비교가 시드 크기와 현금흐름에 중립적인가

현재 화면의 계좌 성과가 `평가손익 변화 / 현재 매입원가`에 가까우면 아래 문제가
생길 수 있다.

- 새 자금을 투입하거나 B 포지션을 추가하면 기존 수익률이 희석된다.
- 매도한 종목의 실현손익이 누락되거나 분모가 줄어 성과가 왜곡된다.
- “하루 보유종목 평균 등락률”과 “실제 계좌 수익률”이 섞인다.

권장 분리안을 검토해 달라.

1. 실제 현금 포함 NAV 기반 일간 수익률 또는 현금흐름 중립 TWR
2. A/B 각각 배정 시드 대비 수익률 + 시드 사용률
3. 장 시작 보유종목의 동일가중 평균 등락률(종목 선택 품질)
4. 같은 장·같은 기준시각의 지수 전일종가 대비 수익률
5. 최대낙폭은 위 수익률 시계열의 누적 NAV 기준

“변동성”은 표준편차/ATR 같은 별도 개념이므로 단순 하루 등락률 비교에는
“등락률” 또는 “수익률”이라고 표시하는 것이 맞는지도 확인해 달라.

## 4. 반드시 실행해 볼 장애 주입 순서

최소 아래 순서를 각각 자동 테스트로 재현 가능한지 평가한다.

1. BUY ACK → 잔고 증가 → 체결내역 지연 → 다음 매수 사이클
2. BUY 부분체결 → 잔량 미체결 → 가격 손절 이탈
3. SELL ACK(filled=0) → 다음 사이클 → 뒤늦은 부분/전체체결
4. 첫 매수 직전 파수꾼 하트비트 없음/오래됨
5. 같은 종목에 1차 주문과 계획 주문 예약이 함께 존재
6. A/B 각각 한도 이내지만 합계가 총시드+완충액을 초과
7. GET/POST 첫 요청이 `EGW00201` → 재시도와 다른 프로세스 호출이 동시에 발생
8. 원장 append 직전/직후 프로세스 강제 종료, 마지막 줄 부분 손상
9. 브로커 잔고 API 실패 + 공개 feed에는 이전 보유가 남아 있음
10. 시장가 급변으로 주문 예상금액보다 실제 체결금액이 커짐
