# GPT 검토 요청용 프롬프트 — 자동매매 배치 인프라 신뢰성 (아래 전체를 붙여넣고, 이어서 OPERATIONS.md 전문을 붙이세요)

---

너는 15년 경력의 SRE(사이트 신뢰성 엔지니어)이자 트레이딩 시스템 인프라 설계자야. 지금부터 내가 운영 중인 **서버리스 자동매매 배치 시스템**의 운영 문서를 줄 테니, 신뢰성 관점에서 비판적으로 검토해줘.

## 전제 (바꿀 수 없는 제약)

1. **비용 0원 유지**: 유료 서버·유료 클라우드·유료 모니터링 도입 제안은 받지 않는다. 무료 티어 서비스 조합까지는 허용.
2. **GitHub 중심 유지**: 코드·CI·호스팅이 GitHub에 있고, 이 구조 자체를 갈아엎는 제안(AWS로 이전 등)보다는 **이 구조 안에서의 보강**을 원한다. 단, 구조 자체의 치명적 결함이 있다면 지적해도 된다.
3. **관리 부담 최소**: 운영자는 개발자가 아니고, 하루 5분 이상 손이 가는 운영은 실패한 설계다.
4. **모의투자 단계**: 실제 돈은 아직 안 걸려 있다. 단 곧 실계좌(토스 API) 연동 예정이라, "실거래라면 치명적일 것"을 미리 지적해주면 가치가 크다.
5. 문서의 "장애 분석"(§6)과 "알려진 한계"(§8)에 이미 적힌 내용은 반복하지 마라. 반복한다면 "왜 기존 대책이 불충분한지"를 구체적으로 붙여라.

## 검토해줬으면 하는 것 (우선순위순)

1. **크론 드랍 대응의 완성도**: 오프피크 분 이동 + 워치독 자가치유 + 수동 탈출구 조합으로 충분한가? GitHub 스케줄러가 반복적으로 불안정할 때 남는 시나리오는? 외부 크론(PAT + cron-job.org)이 유일한 답인가, 더 나은 무료 대안이 있나? (예: Cloudflare Workers cron trigger 무료 티어, Google Apps Script 시간 트리거 등 — 각각의 신뢰성·보안·관리 부담 비교)
2. **상태 영속성 리스크**: 자동매매 계좌 상태가 `actions/cache`에만 있다(7일 미사용 시 소멸, GitHub이 임의 evict 가능). 원자적 저장 + .bak + 매일 빌드로 갱신 중이지만 — 캐시가 통째로 날아가는 시나리오(연휴 + 장애 조합 등)와 대비책은? git 커밋으로 상태를 백업하는 것의 장단점은?
3. **실거래 전환 시 치명 요소**: 15분 폴링 + best-effort 스케줄러 구조에서 실계좌 손절 관리를 해도 되는가? "실거래는 별도 상시 프로세스(사용자 PC/라즈베리파이 등)가 손절만 담당"하는 분리 설계가 필수인가?
4. **Pages 배포 의존성**: 매매는 배포와 분리돼 있지만, 사용자가 보는 대시보드·알림봇이 읽는 signals.json이 Pages에 있다. Pages 장애 시 알림봇도 낡은 신호를 읽는데(제안 알림 부정확), 이 결합을 끊을 방법은? (예: 아티팩트 직접 조회, gist 미러 등)
5. **텔레그램 단일 채널 리스크**: 모든 경보가 텔레그램 하나로 간다. 봇 토큰 만료·API 장애·차단 시 무음이 되는데, 무료로 이중화할 가치가 있나?
6. **보안**: PAT를 외부 크론 서비스에 넣는 방안의 위험(서비스 유출 시 repo Actions 조작 가능)과 최소권한 구성. 커밋 메시지 마커(`[update-top]`)로 빌드 모드를 바꾸는 설계의 악용 가능성(누가 PR을 머지할 수 있는가 기준).
7. **감시의 감시**: 워치독도 같은 GitHub 크론이라 상관 장애가 난다(실측: 같은 날 둘 다 드랍). "감시자가 죽으면 누가 아는가" 문제의 무료 해법 — 헬스체크 데드맨스위치(healthchecks.io 무료 티어: 핑이 안 오면 이메일) 같은 접근이 이 구조에 맞나?
