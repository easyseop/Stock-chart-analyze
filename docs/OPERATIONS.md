# 운영 기술 문서 — 배치 구조·주기·장애 대응

> 2026-07-07 작성. 배치가 "어떻게, 언제, 무엇으로" 도는지의 단일 참조 문서.

---

## 1. 아키텍처 한 장

```
[스케줄러]                [컴퓨트]              [저장/상태]           [출력]
GitHub cron ─┐
푸시(코드/킥) ├→ GitHub Actions(daily.yml) ─┬→ actions/cache ──── 계좌상태·시세캐시
워치독 킥    ┘         │                    └→ Pages artifact ─→ 웹사이트
                       └→ 텔레그램 API ──────────────────────→ 알림(체결·경보)
```

- **서버 없음.** 모든 연산은 GitHub Actions 러너(빌드당 새 VM)에서 실행.
- **상태 영속**: `actions/cache` — 시세 캐시(`data_cache/`, 5,400여 종목 OHLCV csv.gz),
  자동매매 계좌(`data_cache/autopaper.json`, 원자적 저장+.bak), 어닝 캐시,
  상세페이지 산출물(증분 렌더용 ~900MB).
- **호스팅**: GitHub Pages 정적 사이트. **알림**: 텔레그램 봇 API 직접 호출.

## 2. 워크플로 6개

| 워크플로 | 역할 | 트리거 |
|---|---|---|
| **daily.yml** | 데이터 갱신→분석→자동매매→사이트 생성→배포 (메인) | 크론 + 푸시 + 수동 + 킥 |
| advisor.yml | 매수/도달 **제안** 알림(주문 없음) | 크론(매시 10·40분, 장중) |
| watchdog.yml | 신선도 감시→정체 시 자동 재실행+경보 | 크론(시간당 4회) |
| backtest.yml | 전략 백테스트 리포트 | 크론(토 07:09 KST) |
| lookup.yml | 즉석조회(사이트에서 티커 입력 시 수집) | repository_dispatch |
| telegram-check.yml | 봇 연결 확인 | 수동 |

## 3. daily.yml 트리거와 갱신 모드

한 워크플로가 트리거에 따라 **다른 갱신 범위(MODE)**로 돈다:

| 트리거 | MODE | 하는 일 | 소요 |
|---|---|---|---|
| 크론 `4,19,34,49 0-6 UTC` (한국 장중 09:04~15:49 KST, 15분) | `kr` | 한국주 일봉 갱신 | ~5분 |
| 크론 `4,19,34,49 13-20 UTC` (미국 장중 22:04~05:49 KST, 15분) | `top` | 미국주 상위600+보유 갱신 | ~12분 |
| 크론 `9 22 UTC` (마감후 07:09 KST) | `full` | 전 종목 백필+갱신+어닝 | ~30분+ |
| 코드 푸시(기본 브랜치) | `none` | 재배포만(데이터 그대로) | ~2분 |
| 푸시 커밋 제목에 `[update-top]` | `top` | **강제 신선 빌드(탈출구)** | ~12분 |
| 워치독 dispatch / 수동 | 지정값 | 자가치유 재실행 | — |

※ 크론 분이 **:04/:19/:34/:49(오프피크)**인 이유 → §6 장애 분석 참조.

## 4. 빌드 파이프라인 (daily.yml 내부 순서)

1. 캐시 복원 (시세·계좌·상세페이지)
2. **데이터 갱신** (MODE별 — FDR: 야후→Stooq/네이버 폴백, 요청 간 0.3초 스로틀)
3. 어닝 발표일 갱신 (full만) · 시간봉 80종목 (best-effort)
4. **스크리너** — 여기가 심장:
   - 캐시 전 종목 분석(지표·추세선·게이트) → 추천 선별(`gates.classify`)
   - `gates.audit()` 불변식 검사 — **위반 시 배포 자체 차단**
   - **autopaper 자동매매 한 스텝**: 보유 관리(하드/소프트 손절·+1R·트레일·어닝) →
     대기 주문(부패 재검사·체결) → 신규 진입(쿨다운·일일상한·서킷브레이커·1/3캡)
     → 사후 감사(`_audit_caps`·`_audit_rules`) → **체결/위반 텔레그램**
   - HTML 생성(홈·종목·모의·상세페이지 증분 렌더)
5. 아티팩트 업로드(~185MB) — **실패 시 텔레그램**
6. Pages 배포 (실패 시 90초 대기 후 1회 재시도) → 라이브 스모크체크 — **실패 시 텔레그램**

**핵심 성질: 매매·알림은 4단계에서 완결** — Pages 배포(6)가 죽어도 매매는 정상,
웹 표시만 늦는다. 계좌 상태는 캐시로 다음 빌드에 이어진다.

## 6. 장애 분석 (2026-07-06~07 실측) — 원인과 대책

| # | 증상 | 근본 원인 | 대책(적용됨) |
|---|---|---|---|
| 1 | 크론 9시간 드랍 (미장 세션 무실행) | **GitHub schedule은 best-effort** — 고부하 시 지연·드랍, 특히 **정각 피크(:00/:15/:30/:45)**. 우리 daily가 정확히 그 분에 있었음. 증거: 같은 시간대 오프피크(7·22·37·52) 워치독은 발화 | ① 크론을 오프피크(:04/:19/:34/:49)로 이동 ② 워치독 자가치유(정체→top 재실행) ③ `[update-top]` 푸시 탈출구 |
| 2 | Pages 배포 연속 실패 | GitHub Pages 서비스 장애("try again later") + 재시도 간격 37초로 너무 짧음 | 재시도 전 90초 백오프 + 실패 텔레그램. 매매는 배포와 무관(§4) |
| 3 | 워치독 오탐(08:52 경보) | 45분 임계를 **장외 자연 공백**(마감후 07:12 빌드~09:00 개장)에 적용 — 설계 실수 | 장 시간별 임계: 장중 45분/마감후 150분/장외 검사 생략 |
| 4 | 화면 "155분 정체" 오탐 | 열린 탭의 나이 카운터가 페이지에 박힌 빌드 시각 기준으로 계속 증가 — 실제론 갱신됨 | 3분마다 서버 HEAD 재조회로 실시간 신선도 표시 |
| 5 | 클로드 세션 키퍼 사망 | 플랫폼 제약: 세션 예약 작업은 세션 수면 시 소멸 | 보조 수단으로 강등. 영구 독립 스케줄러는 PAT+외부 크론(사용자 설정 필요) |

**공통 교훈**: 단일 무료 인프라(GitHub)의 best-effort 특성이 근본 한계.
대응 전략은 "안 죽게"가 아니라 **"죽으면 반드시 알고, 스스로 복구"** —
모든 실패 경로에 텔레그램 + 자가치유가 붙어 있는 이유.

## 7. 감시·자가치유 계층 (현재)

1. **워치독** (GitHub 크론, 시간당 4회, 오프피크): 장중 45분 정체 → `update=top`
   재실행 + 텔레그램. 장외는 검사 생략.
2. **실패 즉시 알림**: 빌드 실패/배포 실패/규칙 위반(비중·쿨다운)/알림 폭주 —
   각각 텔레그램 자동 발송.
3. **클로드 세션 키퍼** (30분, 세션 생존 시): 정체 감지 → 자동 킥(사용자 승인) — 보조.
4. **수동 탈출구**: 커밋 제목 `[update-top]` 푸시 = 즉시 신선 빌드.
5. (권장·미설정) **외부 크론 + PAT**: GitHub 전체 장애에도 독립적인 유일한 층 —
   cron-job.org에서 15분마다 workflow_dispatch 호출. 사용자 토큰 발급 필요(10분).

## 8. 알려진 한계 (정직하게)

- GitHub 스케줄러/Actions/Pages가 **통째로** 죽으면 5번(외부 크론) 없이는 무대책.
  단, 매매 공백일 뿐 계좌 상태는 안전(원자적 저장 + 캐시 체인).
- 15분 폴링 구조상 빌드 간 가격 이동은 다음 빌드에서 체결(슬리피지로 실현).
- actions/cache는 7일 미사용 시 소멸 — 매일 빌드가 도는 한 문제없음(주말 2일 < 7일).
