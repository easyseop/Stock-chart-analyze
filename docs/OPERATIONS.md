> 2026-07-07 작성. 배치가 "어떻게, 언제, 무엇으로" 도는지의 단일 참조 문서.

## 1. 아키텍처 한 장

```
[스케줄러]                [컴퓨트]              [저장/상태]           [출력]
GitHub cron ─┐
푸시(코드/킥) ├→ GitHub Actions(daily.yml) ─┬→ actions/cache ──── 계좌상태·시세캐시
워치독 킥    ┘         │                    └→ Pages artifact ─→ 웹사이트
                       └→ 텔레그램 API ──────────────────────→ 알림(체결·경보)
```

- **서버 없음.** 모든 연산은 GitHub Actions 러너(빌드당 새 VM)에서 실행.
- **상태 영속**: `actions/cache` — 시세 캐시(`data_cache/`, 5,400여 종목 OHLCV csv.gz),
  자동매매 계좌(`data_cache/autopaper.json`, 원자적 저장+.bak), 어닝 캐시,
  상세페이지 산출물(증분 렌더용 ~900MB).
- **호스팅**: GitHub Pages 정적 사이트. **알림**: 텔레그램 봇 API 직접 호출.

## 2. 워크플로 6개

| 워크플로 | 역할 | 트리거 |
|---|---|---|
| **daily.yml** | 데이터 갱신→분석→자동매매→사이트 생성→배포 (메인) | 크론 + 푸시 + 수동 + 킥 |
| advisor.yml | 매수/도달 **제안** 알림(주문 없음) | 크론(매시 10·40분, 장중) |

| lookup.yml | 즉석조회(사이트에서 티커 입력 시 수집) | repository_dispatch |
| telegram-check.yml | 봇 연결 확인 | 수동 |

## 3. daily.yml 트리거와 갱신 모드

한 워크플로가 트리거에 따라 **다른 갱신 범위(MODE)**로 돈다:

| 트리거 | MODE | 하는 일 | 소요 |
|---|---|---|---|
| 크론 `4,19,34,49 0-6 UTC` (한국 장중 09:04~15:49 KST, 15분) | `kr` | 한국주 일봉 갱신 | ~5분 |
| 크론 `4,19,34,49 13-20 UTC` (미국 장중 22:04~05:49 KST, 15분) | `top` | 미국주 상위600+보유 갱신 | ~12분 |
| 크론 `9 22 UTC` (마감후 07:09 KST) | `full` | 전 종목 백필+갱신+어닝 | ~30분+ |
| **CF Worker / 수동 dispatch (`fast`)** | `fast` | **매매 차선(A1)** — 보유·대기·후보(≤80)만 시세→자동매매→피드. 렌더·배포 없음. 벌크와 분리된 동시성 그룹이라 렌더 정체(F4)에 안 막힘 | **~1~3분** |
| 코드 푸시(기본 브랜치) | `none` | 재배포만(데이터 그대로) | ~2분 |
| 푸시 커밋 제목에 `[update-top]` | `top` | **강제 신선 빌드(탈출구)** | ~12분 |
| 워치독 dispatch / 수동 | 지정값 | 자가치유 재실행 | — |

**fast 차선 안전장치(Phase A)**: ① 매매 분산 락 — state 브랜치 push 원자성으로
fast/bulk 동시 매매 차단, 해제는 `scripts/state_backup.sh`가 스냅샷과 **같은
커밋**으로(임계구역=매매→스냅샷) ② 계좌 최신성 채택 — `saved_at` 비교로 낡은
cache 사본이 최신 계좌를 덮지 않음 ③ 시세 낡음(30분+) 종목 신규 진입·체결 금지
+ 보유 종목 정체 텔레그램(F5) ④ 장중 코드변경 전체 재렌더 금지 → 장외로 지연
(F4). guard: 장외이거나 실빌드 12분 내면 no-op. 발사·검증은 `infra/cf-worker/`.

※ 크론 분이 **:04/:19/:34/:49(오프피크)**인 이유 → §6 장애 분석 참조.

## 4. 빌드 파이프라인 (daily.yml 내부 순서)

1. 캐시 복원 (시세·계좌·상세페이지)
2. **데이터 갱신** (MODE별 — FDR: 야후→Stooq/네이버 폴백, 요청 간 0.3초 스로틀)
3. 어닝 발표일 갱신 (full만) · 시간봉 80종목 (best-effort)
4. **스크리너** — 여기가 심장:
   - 캐시 전 종목 분석(지표·추세선·게이트) → 추천 선별(`gates.classify`)
   - `gates.audit()` 불변식 검사 — **위반 시 배포 자체 차단**
   - **autopaper 자동매매 한 스텝**: 보유 관리(하드/소프트 손절·+1R·트레일·어닝) →
     대기 주문(부패 재검사·체결) → 신규 진입(쿨다운·일일상한·서킷브레이커·1/3캡)
     → 사후 감사(`_audit_caps`·`_audit_rules`) → **체결/위반 텔레그램**
   - HTML 생성(홈·종목·모의·상세페이지 증분 렌더)
5. **계좌 상태 영구 백업** — 스냅샷+월별 원장+기계용 feed를 state 브랜치에 커밋
   (cache 밖 source of truth, 복구 순서: 본파일→.bak→state 브랜치→새 계좌)
6. 아티팩트 업로드(~185MB) — **실패 시 텔레그램**
7. Pages 배포 (실패 시 90초 대기 후 1회 재시도) → 라이브 스모크체크 — **실패 시 텔레그램**
0. (빌드 전) **공회전 가드** — 외부 dispatch(top)인데 라이브가 신선(<40분)이면
   no-op 종료, full은 confirm=FULL 없이는 거부 — PAT 유출 시 피해를 공회전으로 축소

**핵심 성질: 매매·알림은 4단계에서 완결** — Pages 배포(6)가 죽어도 매매는 정상,
웹 표시만 늦는다. 계좌 상태는 캐시로 다음 빌드에 이어진다.

모든 실패 경로에 텔레그램 + 자가치유가 붙어 있는 이유.

## 7. 감시·자가치유 계층 (현재)

1. **워치독** (GitHub 크론, 시간당 4회, 오프피크): 장중 45분 정체 → `update=top`
   재실행 + 텔레그램. 장외는 검사 생략.
2. **실패 즉시 알림**: 빌드 실패/배포 실패/규칙 위반(비중·쿨다운)/알림 폭주 —
   각각 텔레그램 자동 발송.
3. **클로드 세션 키퍼** (30분, 세션 생존 시): 정체 감지 → 자동 킥(사용자 승인) — 보조.
4. **수동 탈출구**: 커밋 제목 `[update-top]` 푸시 = 즉시 신선 빌드.
4.5 **알림 정확성**: advisor가 state 브랜치 feed를 1순위로 읽고(Pages 폴백),
   장중 신호가 25분+ 낡으면 제안 대신 '신호 낡음' 경보(낡은 가격 제안 차단).
4.7 **실거래 대비**: 매도 전용 파수꾼(`bot/sentinel.py`) 개발 완료 — 상시
   프로세스로 손절만 전담(기본 dry-run, 토스 어댑터 자리). STRATEGY 5.5.1 참조.
5. (권장·미설정) **외부 크론 + PAT**: GitHub 전체 장애에도 독립적인 유일한 층 —
   cron-job.org에서 15분마다 workflow_dispatch 호출. 사용자 토큰 발급 필요(10분).
6. **P0 알림 이중화(ntfy)**: 텔레그램이 죽거나 스로틀돼도 **치명 경보**가 도달하는
   독립 채널. 손절·규칙위반·시세정체·신호낡음·파수꾼 매도만 이중 발송(일상 알림은
   텔레그램만 — ntfy 폭주 방지). `NTFY_TOPIC` 미설정 시 전면 비활성(기존과 동일).
7. **체결 회계 지연 감시**: BUY `filled > accounted`가 기본 3사이클 지속되면
   운영자에게 사이클당 요약 1개로 치명 경보. 예약은 계속 유지돼 초과지출 대신
   신규매수가 줄어드는 fail-closed 방향이며, 회계 완료 시 감시 상태를 자동 정리한다.

주문 원장 flock은 비재귀다. 이미 원장 락을 보유한 코드는 `_unlocked` 함수만
호출한다. 파일 잠금 순서는 `ledger > {costbook, kis_positions}` 단방향이고,
KIS·텔레그램 등 네트워크 호출 중에는 파일 락을 보유하지 않는다.

### 7.1 ntfy 켜는 법 (1분, 계정·키 불필요)
1. 휴대폰에 **ntfy** 앱 설치(또는 웹 ntfy.sh) → **추측 불가능한 토픽** 하나 구독.
   예: `stockbot-p0-<아무_긴_랜덤문자열>` (이 문자열이 곧 채널 주소 = 소프트 비밀).
2. GitHub 저장소 **Settings → Secrets → Actions**에 `NTFY_TOPIC` = 그 문자열 추가.
   (시크릿으로 두면 로그에 안 찍힘. 토픽이 새면 누구나 구독 가능하므로 길게.)
3. 끝. 다음 손절/규칙위반부터 텔레그램과 ntfy에 **동시** 도착.
   - 자가 테스트: `NTFY_TOPIC=... python -c "from bot import notify; notify.send('🔴 손절 테스트', critical=True)"` → 앱에 푸시 오면 OK.
   - (선택) `NTFY_SERVER`로 자체 호스팅 ntfy 지정 가능(기본 https://ntfy.sh).
   - 구현 주의: HTTP 헤더는 latin-1만 허용 → 제목/태그는 ASCII, 한글·이모지는 본문만.

### 7.2 긴급 정지 (KILL_NEW_ENTRIES) — 2클릭 브레이크
나쁜 데이터·로직 사고 때 **신규 진입만** 즉시 멈추는 스위치(보유 관리·손절·백업은
계속). 실거래 단계적 kill switch(§7.5)의 1층.
- **켜기**: 저장소 **Settings → Variables → Actions**에 `KILL_NEW_ENTRIES = 1`
  (코드 수정·배포 불필요. 다음 빌드부터 신규 진입/신규 지정가 생성 중단).
  막힌 날 1회 텔레그램+ntfy(P0)로 통지.
- **끄기**: 그 Variable을 지우거나 `0`으로. 다음 빌드부터 정상 진입 재개.
- **범위**: 신규 진입/신규 지정가 생성만. 이미 걸린 지정가 체결·손절·트레일·백업은
  계속(보호는 유지, 확대만 정지). 더 센 정지(전 주문 취소)는 실거래 단계에서 추가.

## 8. 알려진 한계 (정직하게)

- GitHub 스케줄러/Actions/Pages가 **통째로** 죽으면 5번(외부 크론) 없이는 무대책.
  단, 매매 공백일 뿐 계좌 상태는 안전(원자적 저장 + 캐시 체인).
- 15분 폴링 구조상 빌드 간 가격 이동은 다음 빌드에서 체결(슬리피지로 실현).
- actions/cache는 7일 미사용 시 소멸 — 매일 빌드가 도는 한 문제없음(주말 2일 < 7일).
