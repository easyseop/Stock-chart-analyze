## 2. 이 연동이 해결하는 것 (지금 시스템의 근본 한계)

| 현재 한계 | 토스 연동 후 |
|---|---|
| 시세 15분~수분 지연(야후/Stooq 무료) | 토스 정규 시세 — **실제 체결 가능한 가격** |
| 종목 단위 무음 정지(F5: TSLA 6h 동결) | 우리가 거래하는 증권사 소스 → 스로틀 사실상 소멸 |

| 주문이 시뮬레이션 | 실제 매수/매도 집행 |
| "화면 가격 ≠ 매매 가격" 불일치 | 조회·매매 동일 소스 → 불일치 소멸 |

## 3. 가격 조회 제약과 우리 예산 (한도 안 걸림 증명)

**제약 ① 실시간 웹소켓 미공개 → REST 폴링.**
우리 전략은 일봉 기준 스윙이라 **1분 폴링으로 충분**. 웹소켓 나오면 손절 지연만
초 단위로 더 짧아짐(교체는 어댑터 내부 일).

**제약 ② Rate limit.** 우리 규모로 계산:
```
보유 4 + 후보 80 = 시세 ~84건 / 1분 폴링 = 초당 1.4건  ≪ 분당 수백 건 한도  ✅
```
시세는 확실히 여유. **진짜 병목은 계좌 조회다(2차 검토 지적 — 채택).**
`rate limit은 평균이 아니라 버스트에서 깨진다`: 잔고·보유·주문가능수량·매수가능금액·
open orders·주문상세·체결조회가 **모두 같은 account bucket(초당 1건)을 공유한다고
보수적으로 가정**하고 설계한다(실측 전까지). 그러지 않으면 루프B(주문 직전 조회)와
루프C(파수꾼)가 같은 1초에 몰려 429/무통보 제한 → **하필 손절 직전 조회가 실패**.

**account 예산 규율(실측 전 기본):**
```
account_bucket: 1 req/s, burst 1 — 모든 계좌/주문조회 endpoint 공유 가정
루프A: 계좌 조회 안 함(또는 1분 1회 스냅샷만)
루프B: 주문 직전 조회 최우선권. broker_available 재조회는 필수
루프C(파수꾼): 매 폴링 계좌 조회 금지 — 평상시 시세만, stop 근접/이탈 시에만
              보유수량 재조회. 보유 스냅샷 30~60초 TTL.
```
시세는 배치 조회 우선, 모든 계좌 호출은 단일 리미터 통과 + 지수 백오프 재시도.

## 4. 3중 루프 구조 (실매매 시)

```
[서버 $6/월 · 상시]
 ┌─ 루프A: 시세→전략 (1분)  ── 토스 시세 폴링 → 지표/게이트 → 자동매매 판단
 ├─ 루프B: 주문 집행 (이벤트)── 판단이 '진입/청산'이면 토스 주문 + 원장 기록
 └─ 루프C: 파수꾼 (10~20초) ── 보유 손절선 감시, 이탈 시 매도(읽기=토스 시세)
                                 ★ 브로커 서버측 stop 지원 시 매수 직후 등록(0차)
[GitHub · 무료] 5,400종목 풀스캔·렌더·Pages (화면 담당, 매매와 분리)
```

### 4.1 시세 조회 (루프A·C 공통)
- 인증: **단일 token_manager**가 토큰을 소유 — 50분 선제 갱신 + **refresh lock**
  (루프 3개가 동시에 갱신하는 thundering herd 방지). 401 발생 시 한 번만 강제
  refresh 후 재시도, 갱신 실패=P0. 루프별로 토큰 갱신을 흩뿌리지 않는다(2차 검토).
- 조회: 보유+후보를 **배치 시세 API**로 1분 1회. 개별 종목당 `last_price`,
  `quote_ts`(시각) 확보. **quote_ts 나이 > 10~30초면 손절 판단에 쓰지 않음**(지연 방어).
- 폴백: 토스 조회 실패/누락 종목은 기존 FDR(야후/Stooq)로 폴백 → 그 종목은
  `is_stale_for_trading=true` 태깅(낡은 소스로 신규 주문 금지).

### 4.2 매매 시 시세 조회 (루프B — 주문 직전)
주문은 "판단 시점 가격"이 아니라 **집행 직전 최신가로 재확인**한다:
1. 주문 직전 해당 종목 **단건 시세 재조회**(quote_ts 신선 확인)
2. **브로커 실보유 수량 재조회**(Account) — `intended_qty ≤ broker_available`
3. 지정가/시장가 결정 → 주문 전송 → 응답 상태를 **주문 원장**에 기록
4. timeout이면 **UNKNOWN** — 즉시 재주문 금지, open orders/positions 대사 후 잔여만

### 4.3 손절 집행 (루프C — 파수꾼)
- 10~20초 폴링(웹소켓 나오면 스트림). **평상시엔 시세만 조회**(계좌 X). 손절선
  근접/이탈 시에만 보유수량 재조회(30~60초 TTL 스냅샷) — account 버킷 보호(2차 검토).
- **매도 허용 6조건**(sentinel.py 스펙): 브로커 실보유>0 ∧ open position 일치 ∧
  포지션 정체성(opened_at·seq) 일치 ∧ quote 신선 ∧ stop 래칫(하향 금지) ∧
  intended≤available.
- **호가 공백 방어**: last_price 신선해도 매도 호가가 얇으면 시장가가 크게 미끄러짐
  → 가능하면 orderbook(bid/ask) 확인, 손절 시장가 vs 지정가+재시도 정책 명시.
- **매수 경로 없음**(파수꾼은 손절 전담 — 코드 grep 테스트로 영구 검증).

## 5. 전략은 그대로 (실매매라고 안 바뀜)

전략·게이트·사이징은 **모의와 100% 동일 함수 재사용**한다(차선·환경이 달라도
같은 데이터엔 같은 결정). 바뀌는 건 "가격 소스"와 "주문이 진짜냐"뿐:
- 진입: 52주 저점권 전환 초입, 체크리스트 게이트, 손절폭 3구간 전술
- 사이징: 1% 리스크 역산(손절폭 좁으면 크게·넓으면 작게), 종목당 1/3 상한
- 청산: 하드/소프트 손절·+1R 절반·트레일 래칫·어닝 D-1·타임스탑
- 안전장치: 쿨다운·하루 진입 ≤3·일일 −2% 서킷브레이커

## 6. 실매매 안전장치 (2차 SRE 검토 반영 — 경계 장애 방어)

| 위험 | 방어 |
|---|---|
| 토큰 만료(주문만 401) | 장전 preflight + 50분 선제 갱신 + auth 실패=P0 |
| 주문 UNKNOWN → 초과매도 | timeout=UNKNOWN, 재주문 금지, open orders 대사 후 잔여만 |
| 부분체결 수량 불일치 | 브로커 포지션이 source of truth, 주문 후 실보유 재조회 |
| 시세 지연 | quote_ts 나이 검증(>10~30초 손절 판단 금지) |
| feed 낡음에 최신 stop 미전달 | 파수꾼 내부 stop 래칫 유지, 마지막 확정 stop 계속 집행 |
| 서버·GitHub·CF 동시 사망 | **브로커 서버측 stop [대조필요]** — 토스 조건주문/stop 지원 여부 **미확인**. 지원 시 매수 직후 등록(0차 방어). **미지원이면 파수꾼이 유일 손절 경로** → 파수꾼 하트비트+P0+수동 절차 강화, 초기 리스크 0.1~0.25%로 더 보수적 |
| 액면분할/기업행위 | 수량 불일치 시 신규 주문 금지 + 수동 리뷰 |
| 멱등 | `{broker}:{account}:{symbol}:{opened_at}:{seq}:{action}:{stop_version}` |
| P0 알림 단일점 | 텔레그램 + ntfy 이중화 |

## 7. 도입 단계 (리스크 0 → 소액 → 확대)

| 단계 | 토스 사용 범위 | 주문 | 리스크 |
|---|---|---|---|
| **0. 시세 읽기 전용 (지금 가능)** | 시세만(읽기) | 가상 | **0** — 모의 정확도만 실전급으로↑ |
| **1. 그림자(Shadow) 2주+** | 시세+계좌 조회 | 가상(dry-run) | 0 — 브로커 상태↔우리 기록 일치 검증 |
| **1.5. 주문 dry-run/최소단위** | +주문 API 상태전이 확인 | 최소단위 1건 수동 | 극소 — 주문 응답 모델 실측 |
| **2. 마이크로 라이브** | 시세+계좌+주문 | **실주문 0.1~0.25%** | 소액 — 동시 1~2종목·하루 1건·한 시장 |
| **3. 제한 라이브** | 전체 | 실주문 0.25~0.5% | Stage2 무사고 후 |
| **4. 정상 후보** | 전체 | 실주문 1% 후보 | 주문 50~100건 무사고 + 장애주입 통과 |

**Stage 2 진입 전 필수(2차 검토)** — ✅=스캐폴드 구현·테스트 완료(모의):
· ✅ **주문 원장 상태전이**(`bot/ledger.py`: submitted→filled/partial/rejected/unknown,
  append-only JSONL) · ✅ **UNKNOWN 처리**(종목 잠금→대사 전 재발주 금지) ·
  ✅ **부분체결 reconcile**(실체결 대사 후 **잔여만** 재주문) · ✅ **내부 멱등**
  (`{broker}:{account}:{code}:{opened}:sell` + 시도별 `#n`) · ✅ **kill switch**
  (`KILL_NEW_ENTRIES`) · ✅ **P0 ntfy 이중화** ·
  ⬜ 실 브로커 주문상태 조회 API 연결(`broker.order_status` 자리 — 토스 응답 실측) ·
  ⬜ client_order_id 지원 확인 · ⬜ broker-side stop(`/conditional-orders`) 실측 ·
  ⬜ 장전 preflight 5일 연속 성공.
각 단계 통과 기준·장애 주입 테스트는 `RELIABILITY_PLAN.md` §6 참조.
> 원장 스캐폴드는 모의 브로커로 UNKNOWN→잠금→대사→잔여재주문 경로까지 검증됨
> (`tests/test_ledger.py`, `tests/test_sentinel.py` ⑧). 실주문 붙일 때 토스
> `order_status`/`conditional-orders` 응답만 어댑터에 채우면 된다.

## 7.5 증권 실계좌 운영 함정 (2차 검토 Q5 — 실매매 전 필수 확정)

SRE 장애는 반영됐으나 "증권 실계좌"의 함정은 별도로 확정해야 한다:

| 항목 | 확정할 것 |
|---|---|
| **주문 유형 정책** | 신규=지정가만? / 손절=시장가(슬리피지) vs stop-limit(미체결)? / 장외=금지 or 예약? / 부분체결 잔여=취소·유지·재가격? |
| **환전·외화잔고** | 미국주 매수 시 USD 잔고 부족 처리, 자동환전 여부·시점, 원화 1% 리스크 ↔ 달러 체결금액 차이, 환전 실패 시 주문거부 형태 |
| **T+2·결제·미수** | 매도 직후 현금 즉시 재사용 가능? 결제 전 매수 가능? 미수/신용 비활성 확인, 주문가능금액 ≠ 실제 현금 |
| **기업행위** | 액면분할·병합·**티커 변경·거래정지·상장폐지**·배당락 → 심볼 매핑·수량 불일치 시 신규 주문 금지+수동 리뷰 |
| **API 점검시간** | 토큰발급·계좌조회·주문 불가 시간대, 미국장 중 점검 가능성, 점검 전후 open orders 확인 |
| **앱/API 동시 접근** | 사용자 앱 수동주문 ↔ API 파수꾼 손절 충돌 → `broker position ≠ internal`이면 신규 금지+파수꾼 보호모드+P0 |
| **수수료·세금·소수점** | 미국주 소수점 주문 지원?·최소주문금액·제세금 반영 손익·매도가능수량 반올림 |
| **kill switch** | 신규 진입 전역 중지 → 전 주문 중지 → 파수꾼만 유지 → 파수꾼도 중지 → 수동 청산, 단계별 스위치 |

## 8. 지금 바로 할 수 있는 것 (Stage 0) — ✅ 구현 완료

키가 있으니 **주문·계좌를 안 건드리고 시세만** 붙였다:
1. ✅ `bot/toss.py` — OAuth 토큰 발급/캐시(선제 갱신·401 자동 재발급) + 시세
   배치 조회(`/api/v1/prices`, ≤200건, 읽기 전용). 표준 라이브러리만.
2. ✅ **토스 우선 → 실패 시 FDR 폴백** — `bot/advisor._quote`·`bot/sentinel`
   현재가 조회의 1순위를 토스로. 키 없거나 실패면 조용히 FDR(현행 100% 동일).
3. 자동매매·주문은 **여전히 가상** → 리스크 0, 데이터 품질만 실전급.
4. ✅ 검증: `tests/test_toss.py`(키게이트·파싱·401재발급·시크릿 비노출).

**설계 안전판**: 키 미설정=어댑터 전면 비활성, 모든 실패=예외 없이 빈 결과→폴백.
그래서 엔드포인트 추정이 틀려도 최악이 "지금과 동일(FDR)"이지 장애가 아니다.

**환경변수(값은 절대 코드·채팅·로그·커밋 금지 — GitHub Actions 시크릿으로만):**

```
TOSS_BASE_URL        (선택) 기본 https://openapi.tossinvest.com
```
**사용자 확인 절차(키 설정 후)**: 로컬에서 `TOSS_CLIENT_ID=… TOSS_CLIENT_SECRET=…

그다음 Actions 시크릿에 두 값을 넣으면 배치가 자동으로 토스 시세를 1순위 사용.

**다음(Stage 0.5, 더 큰 효과)**: fast lane/autopaper의 "현재가=일봉 마지막 종가"를

## 9. 구현 착수 시 실제 응답으로 확정할 것 (2차 검토 Q1~Q10 — 감으로 답 금지)

이 10개는 공식 문서/실제 API 응답으로만 답할 수 있다. Stage 0/1에서 하나씩 실측해
이 문서를 갱신한다. **모두 확정 전 Stage 2(실주문) 금지.**

1. 시세/계좌/주문 rate limit이 **독립 bucket인가 합산인가**
2. 계좌 초당 1건에 잔고·주문가능수량·open orders·주문상세·체결조회가 **다 포함**되나
3. 미국주 시세: 정규장/프리/애프터/주간거래 중 어디까지·어떤 지연으로
4. **quote_ts**가 응답에 있나 — 거래소 시각인가 토스 수신 시각인가
   → **부분 확정**: `/api/v1/prices` 응답에 `timestamp`(ISO8601, 체결 없으면 null)
   존재. 거래소 시각 vs 토스 수신 시각 구분은 실측 필요.
5. 주문에 **client_order_id/멱등키**를 넣을 수 있나(`/api/v1/orders` 스키마 실측)
6. timeout 후 주문 상태를 어떤 엔드포인트로 안정 확인 → `/api/v1/orders/{orderId}` 존재
7. 부분체결·미체결취소·정정의 **상태 전이** 표현(`orders`·`orders/{id}/cancel|modify`)
8. **서버측 stop/조건주문** 지원 여부(0차 방어 존폐를 가름)
   → **지원 확인**: `/api/v1/conditional-orders`(생성/조회/취소/정정) 존재.
   stop vs stop-limit·미국주 지원·트리거 조건 세부는 실측 필요.
9. API 점검시간·토큰갱신 실패 시 주문/조회 실패 형태
10. 앱 주문 ↔ API 주문 동시 존재 시 source of truth
