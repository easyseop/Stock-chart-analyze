## 1. 사건 — 무엇이 실제로 일어났나 (2026-08-10 실측)

1. 22:31:14 KST, 파수꾼이 TAP(NYSE, legacy 이관 포지션 80주)의 **타임스탑 21일
   매도 80주**를 접수시켰다. 접수는 성공(ODNO `0000038291`, state=`ack`).
   원장 행: `key=xe:TAP:time:2026-07-20`, intended=80, filled=0, price=42.97.
2. 브로커에서 이 주문은 **체결 0으로 종결**됐다(거절 추정 — TAP은 8/6에도
   절반익절 매도가 거절된 전력, docs/CODEX_HANDOFF.md §33). 그러나 원장 행은
   `ack`로 남았다. buyloop 재시작으로 부팅 리졸버(`kis_boot._resolve_acks`)를
   돌려도 해소되지 않았다.
3. 결과: `l1_readiness`의 `no_open_orders` 게이트가
   `원장 브로커주문=1, 브로커 열린주문=0`으로 **NO-GO** — 주말 플래핑발 L1을
   L0로 복구하는 절차 전체가 이 전표 하나에 막혔다.
4. 수동 복구: 브로커 실측(TAP 잔고 80주 그대로, 미체결 0) 확인 후
   `ledger.reconcile("xe:TAP:time:2026-07-20", 0)` → state=rejected → GO → L0.

핵심: **사람이 한 판정("미체결에 없음 + 체결내역에 없음 + 잔고 불변 = 거절
종결")을 코드가 할 수 없어서** 운영자가 새벽에 원장 수술을 해야 했다.

## 2. 원인 — 왜 리졸버가 못 잡았나 (코드 실측)

`kis_boot._resolve_acks`의 증명 경로는 두 개뿐이다:

- **경로 A** `resolve_acks_from_rows`: 체결내역(ccnl)·미체결(nccs) 행에서
  ODNO를 찾아 확정. → **거절 주문은 체결내역에 행이 없다.** 못 찾으면 방치.
- **경로 B** `resolve_acks_by_balance`: 잔고 delta로 full-fill을 보수적 확정.
  → SELL 거절이면 잔고가 그대로(80→80)인데, "잔고 불변"은 '거절'과
  '아직 체결 대기'를 **구분할 수 없어** 건드리지 않는 게 설계상 맞았다.

즉 "거절"은 **부재(不在)로만 증명되는 상태**인데 부재 증명 경로가 없다.
부수 결함: `_resolve_acks` 전체가 `except Exception: return []`로 침묵해
조회 실패가 몇 사이클째 계속돼도 로그·알림·진단 어디에도 안 보인다.

## 3. 구현 요구사항 (4건)

### R1. 부재 증명 자동 정산 (핵심)

`ack/submitted` 행에 대해 아래 **전 조건이 동시에 성립할 때만** 해당 행을
`ledger.reconcile(key, 0)`(= rejected)으로 자동 정산한다:

1. `age ≥ REJECT_ABSENCE_MIN_S` (신규 상수, 기본 **600초**;
   기존 `ACK_AGE_MIN_S=90`보다 훨씬 보수적으로 — 지연 체결 오독 방지)
2. 해당 시장의 **미체결 조회가 성공**했고, 그 결과에 이 ODNO가 **없다**
3. 해당 시장의 **체결내역 조회가 성공**했고, 그 결과에 이 ODNO가 **없다**
   (ODNO 비교는 반드시 기존 정규화 키 — PR #111의 선행 0 제거 — 사용)
4. **잔고 조회가 성공**했고(US는 3거래소 전부 성공한 complete snapshot만),
   SELL이면 해당 종목 수량이 `hldg_before` 그대로, BUY면 증가분 0
5. 위 2·3·4의 응답이 **모두 신뢰 가능 형태**(rt_cd=="0", 연속조회 키 없음 등
   기존 보수 파싱 규칙과 동일 수준)

**정산 시 원장 이벤트에 근거를 남긴다**: `reason="absence-proof"` 및
각 조건의 실측값(미체결 0·체결 0·잔고 불변). 알림 1회:
`"⚠️ 매도 거절 종결(부재 증명) — TAP 80주 · 보호는 유지"` 형식(SELL이면
critical=True — 계획된 매도가 안 나갔다는 뜻이므로).

### R2. 리졸버 침묵 제거

- `_resolve_acks`의 포괄 except를 유지하되(부팅을 못 깨는 원칙), **실패
  사유를 로그로 남기고 연속 실패 카운터를 모듈 상태로 노출**한다.
- `/진단`(kis_telegram `_diag_text`)에 `대사: 마지막 성공 N분 전 · 연속 실패 M회`
  한 줄 추가. 알림은 연속 실패가 임계(기본 6회 = 약 1시간) 도달 시 1회만.

### R3. 거절 사유 저장

- 경로 A에서 **거절/취소 상태의 행을 발견하면**(모의가 제공하는 범위에서)
  `msg_cd`·`msg1`을 원장 이벤트 meta에 저장하고 알림에 포함한다.
- 부재 증명(R1) 정산은 사유를 알 수 없으므로 `"사유 미상(부재 증명)"`으로
  기록 — **사유를 지어내지 않는다.**
- 저장 문자열은 길이 제한(예: 200자)·제어문자 제거. 시크릿·계좌번호 절대 금지.

### R4. ack 방치 경보 (관측 계층)

- `ops_status`(읽기 전용 계층)에서: `submitted/ack` 상태로
  `ACK_STUCK_ALERT_S`(기본 1800초) 초과한 행이 있으면 텔레그램 경보.
  행별 1회(해소 전 재발송 금지), 해소되면 1회 회복 알림.
- ops 스냅샷 JSON에 `stuck_acks: N` 필드 추가(수량만, 종목·금액 없이 —
  기존 무시크릿 원칙).

### R0. (구현 전 실측) TAP 거절 원인 조사

구현 착수 전에 Oracle에서 해외 주문내역(체결·거절 포함) 조회로 ODNO
`0000038291`의 상태·메시지를 실측하고 결과를 이 문서 하단에 추기한다.
모의서버가 거절 행 자체를 안 보여주면 그 사실이 곧 R1의 존재 이유다.
TAP이 구조적으로 매도 불가(legacy 이관 특성 등)로 판명되면 별도 보고 —
타임스탑이 매 세션 거절을 반복하게 두지 않는다.

## 4. 주의점 (적대 검토에서 반드시 볼 것들)

- **부재 증명의 치명 함정 = 조회 실패를 부재로 오독하는 것.** 다섯 조건 중
  하나라도 "조회 실패/None/형식 불신"이면 **아무것도 하지 않는다**(다음
  사이클). `[] (빈 결과)`와 `None (실패)`를 절대 혼동하지 말 것 — 기존
  `_broker_open_count`류의 보수 파싱을 재사용하고, 새로 느슨한 파서를 만들지
  않는다.
- **레이스**: "미체결에 없음+체결에 없음"이 성립하면 주문은 브로커에서 종결
  상태다 — 이후에 체결될 수 없다. 단, 조회 시점 사이의 레이스를 줄이기 위해
  **미체결 → 체결내역 → 잔고 순서로 조회**하고, 잔고에서 모순(SELL인데 수량
  감소)이 보이면 자동 정산하지 말고 UNKNOWN급 경보로 사람을 부른다.
- **부분 체결**: 체결내역에 이 ODNO의 부분 체결 행이 있으면 부재가 아니다 —
  기존 경로 A가 처리하게 두고 R1은 손대지 않는다(조건 3이 자연 차단).
- **국내(KR)**: 모의는 `inquire-psbl-rvsecncl` 미지원(msg_cd=90000000) —
  미체결 부재 증명은 기존 mock 전용 폴백(`domestic_unfilled_orders`)의 강한
  검증 계약을 그대로 따르고, **live에서 폴백 사용 금지 계약을 깨지 않는다.**
- **planned 행은 대상 아님**: R1은 브로커에 실제 제출된 행(state
  submitted/ack + ODNO 보유)만. planned/미전송 leg는 기존 처리 유지.
- **reconcile 의미 불변**: `ledger.reconcile`의 시그니처·상태 전이를 바꾸지
  않는다. R1은 호출자를 추가할 뿐이다.
- **주문 발주 경로 무변경**: 이 지시서 어디에도 신규 주문·취소·kill 변경은
  없다. `tests/test_ops_status.py::test_read_only_no_order_paths`가 ops_status
  쪽 가드다(문자열 검사 — 주석에 금지 단어를 쓰면 걸린다, 실측).
- **알림 폭주 금지**: R1·R2·R4 모두 행별/사유별 1회 원칙. 기존
  `NOTIFY_MODE=trade_only` 필터를 통과해야 하는 알림은 critical 또는
  trade/query 카테고리 규칙을 확인하고 선택할 것.
- **뮤테이션 검증 전 반드시 커밋**(8/5 실측 사고: git checkout 복원으로
  미커밋 리팩터 소실). 증거는 실패 테스트명 + 종료코드를 원문 인용.
