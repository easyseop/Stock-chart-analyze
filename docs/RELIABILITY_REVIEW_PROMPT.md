# 신뢰성·인프라 검토 요청 (GPT용) — 서버리스 자동 모의투자의 크론 불안정 문제

> 이 문서 하나만 읽고 평가해달라. 배경 지식 없이 판단 가능하도록 자기완결로 작성했다.
> **요청: ① 아래 진단이 정확한지 ② 제안(3계층 분리 + CF Worker + 파수꾼)이
> 최선인지, 놓친 더 단순하거나 더 견고한 대안이 있는지 ③ 실거래 전환 시
> "장애가 손실로 이어지지 않는" 설계에 구멍이 없는지 — 구체적 실패 시나리오와
> 함께 지적해달라.**

## 0. 시스템 요약 (이것만 알면 됨)

- **무엇**: 차트 기반 스크리너 + **서버사이드 자동 모의투자**(가상 시드 1억). 전략은
  "하락→상승 전환 초입을 52주 저점권에서 매수, ATR 기반 손절, 손익비 1:2".
- **인프라**: **서버 없음.** 전 연산이 GitHub Actions(빌드당 새 VM)에서 돈다.
  호스팅=GitHub Pages(정적), 알림=텔레그램 봇 API, 상태 저장=actions/cache +
  state 브랜치(스냅샷·원장).
- **주기**: 원래 GitHub 크론 15분. 한 빌드가 **[시세 수집 → 5,400종목 지표 분석 →
  자동매매 1스텝(손절·익절·신규진입) → 5,400 상세페이지 렌더 → Pages 배포]**를 순차 수행.
- **제약**: 비용 0원 지향, 운영자는 비개발자 1인(하루 5분), 아직 모의투자 단계.
- **이미 갖춘 방어**: 외부 크론(cron-job.org)로 dispatch 이중화, 워치독 자가치유,
  오프피크 크론, 공회전 가드, state 브랜치 계좌 백업, 전 실패 경로 텔레그램,
  매도 전용 파수꾼(sentinel.py — 손절만 전담, 매수 경로 없음, dry-run 완성).

## 1. 문제 진단 — "GitHub Actions가 자꾸 죽는다" (전부 실측)

| # | 고장 모드 | 빈도 | 실측 증거 | 매매 영향 |
|---|---|---|---|---|
| F1 | **GitHub 크론 드랍**(best-effort) | 상시 | 2026-07-07 하루 schedule 실행 **7회 / 기대 ~60회 = 드랍 88%**. 전날 밤 9시간 전멸 | 가격·매매가 15분→최대 수시간 지연 |
| F2 | 플랫폼 이벤트 전면 동결 | 드묾 | 7/7 아침 3시간 push·schedule 런 미생성, API dispatch만 생존 | 위와 동일, 더 김 |
| F3 | Pages 배포 실패 | 가끔 | 큐 정체·서비스 오류, 재시도로 회복 | **없음**(매매는 배포 前 완결) |
| F4 | **자초한 정체** — 전체 재렌더 연속 투입 | 1회 | 코드 3연속 커밋 → 5,400페이지 전체 재렌더(각 ~17분)가 `pages` 동시성 그룹 점유 → 가격 빌드 33분+ 밀림 | 가격·매매 지연(운영 실수) |
| F5 | **종목 단위 무음 정지** | 가끔 | 한 종목(TSLA) 데이터소스 스로틀로 6시간 가격 동결. 타 종목은 실시간과 센트 단위 일치 | 그 종목만 낡음 — **경고 없음이 진짜 문제** |
| F6 | 캐시 휘발(계좌 소실) | 과거 | actions/cache 경합으로 즉석조회분 소실 | **해소됨**(state 브랜치 백업) |

**근본 원인**: 무료 GitHub 크론은 "정시 실행을 보장하지 않는 것이 계약 조건"인데,
시스템의 심장(시세 갱신→자동매매)이 그 정시성에 직접 얹혀 있다.

**중요**: 2주 운영·사건 16건 중 **계좌 손상은 0건.** 지금까지의 피해는 전부
"지연"이지 "손실"이 아니다(외부 킥·백업·경보가 작동한 결과).

## 2. 제안 — 정시성 요구로 3계층 분리

같은 파이프라인에 정시성 요구가 다른 세 일이 섞여 있는 게 병목이라고 본다.

| 계층 | 하는 일 | 정시성 요구 | 배정(제안) |
|---|---|---|---|
| L1 분석·렌더 | 5,400종목 스캔, 900MB 페이지 | 낮음(수십 분 지연 무해) | GitHub Actions 유지(무료·무제한이 강점) |
| L2 **시세→매매** | 보유·후보 시세 + 자동매매 1스텝 + 기계용 feed | **중(15분 보장)** | GitHub 실행 + **CF Worker 보장 발사·검증** + **빠른 모드**(L1 렌더 분리, ~3분) |
| L3 **손절 집행**(실거래) | 보유 손절선 감시·매도 | **고(초 단위·상시)** | **상주 프로세스**(파수꾼) — GitHub 밖 별도 호스트 |

### Phase A (모의, 지금)
- A1 **빠른 모드 분리**: 시세+매매+feed만 갱신(렌더·배포 생략, ~3분) → F4 무력화
- A2 **Cloudflare Worker 크론**: 15분마다 발사 + "런이 실제 생겼나" 검증 + 미생성 시
  재시도. CF 크론은 best-effort가 아닌 **보장 실행**(무료 10만 요청/일, 사용 ~200/일) → F1·F2
- A3 **종목별 신선도 스탬프 + 무음 정지 경보**: 데이터 나이 임계 초과 종목 강제
  재수집, 반복 실패 시 텔레그램 → F5
- A4 **재렌더 장중 금지**(코드로): 전체 재렌더는 장외로 지연 → F4 재발 방지

### Phase B (실거래 결정 시)
- B1 파수꾼 상주 가동(Oracle Cloud 무료 티어 또는 $5 VPS) — 손절 전담
- B2 주문 원장 + 부분체결 reconcile + 포지션 정체성 멱등키
- B3 concurrency 전용 그룹 + state lock(주문 이중 발사 차단)
- B4 P0 경보 ntfy 이중화(텔레그램 단일점 제거)
- B5 CF Worker가 파수꾼 하트비트 감시(감시의 감시·데드맨)

## 3. 실거래 장애 매트릭스 (Phase A+B 완료 가정) — 자체 주장

| 장애 | 신규 진입 | **보유 손절** | 계좌 기록 | 결론 |
|---|---|---|---|---|
| GitHub 크론 드랍 | CF 발사 정상 | 파수꾼 정상 | 정상 | 영향 없음 |
| GitHub Actions 전면 장애 | 공백(기회비용) | **파수꾼 계속 집행** | state 보존 | **손실 없음** |
| CF Worker 장애 | GitHub+cron-job 백업 발사 | 파수꾼 무관 | 정상 | 지연만 |
| 파수꾼 호스트 사망 | 무관 | 15분 폴링으로 강등 + **P0 즉시 경보** | 정상 | 알고 대응 |
| 텔레그램 장애 | 무관 | 무관 | 정상 | ntfy로 도달 |
| 데이터소스 스로틀 | 해당 종목 보류 | 파수꾼은 브로커 시세 사용 | 정상 | 영향 최소 |

**자체 결론**: 손절 경로(파수꾼)가 GitHub·CF·텔레그램 어디에도 의존하지 않으므로,
어떤 단일 장애에서도 "손절 불능"이 발생하지 않는다. 최악(GitHub+CF 동시 장애)도
결과는 "신규 진입 공백"이지 손실이 아니다. **← 이 주장이 맞는지 반증해달라.**

## 4. 비용·관리

CF Worker 무료(사용 0.2%) · 파수꾼 Oracle 무료 티어 또는 VPS ~$5/월 · ntfy 무료 ·
cron-job.org 무료 유지. 합계 **0~5$/월**, 관리 **월 ~10분**.

## 5. GPT에게 묻는 질문

1. **진단 정확성**: F1~F6 분류와 "근본 원인=무료 크론 정시성"이 맞나? 놓친 고장 모드는?
2. **제안 적정성**: 3계층 분리 + CF Worker(트리거만) + 빠른 모드가 최선인가?
   - 우리가 기각한 대안: "CF Worker가 시세를 직접 수집"(독립 수집기) — 5,400종목
     수집을 무료티어로 못 돌리고, 매매는 여전히 GitHub 종속이라 **가격·매매 불일치**가
     생겨 기각. 이 판단이 맞나?
   - 더 단순한데 우리가 놓친 것(예: GitHub 크론 완전 폐기하고 cron-job.org 단독 +
     검증만 추가)이 있나? CF Worker가 cron-job.org 대비 실제로 얼마나 나은가?
3. **실거래 무리스크 주장 반증**: §3 매트릭스에서 "손절 불능이 생기는" 시나리오를
   하나라도 만들 수 있나? 특히 파수꾼과 브로커 사이(부분체결·API 인증만료·시세지연·
   네트워크 파티션)에서.
4. **과설계 점검**: 모의 단계에 Phase A 4개가 과한가? 실거래 전으로 미뤄도 되는 건?
5. **파수꾼 위험**: 손절 전담 상주 프로세스 자체가 새 단일점 아닌가? 그게 오작동해
   **잘못 파는**(원치 않는 매도) 리스크는 어떻게 봉쇄하나? (현재: 매수경로 부재 grep
   테스트, 하드/소프트 2연속 확인, 멱등키, 피드 30분+ 낡으면 보호모드)

— 구체적 실패 시나리오와 함께 답해주면 바로 반영한다. 이론적 원칙론보다
"이 조합에서 이렇게 깨진다"가 훨씬 유용하다.
