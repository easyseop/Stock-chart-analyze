## 1. 문제 (2026-08-14 실측)

`bot/kis.py`의 잔고·주문 조회는 **첫 페이지만 요청**한다
(`CTX_AREA_NK200=""`, `CTX_AREA_NK100=""`). 그리고 소비자
(`holdings()`, `positions_detail()`, `kis_reconcile.trusted_response_rows()`)는
응답에 연속조회 키가 남아 있으면 **전체를 신뢰 불가(None)로 버린다**. 잘린
목록을 '미보유'로 오판해 중복매수·보호누락이 나는 것을 막는 정당한 fail-closed
계약이다. 문제는 **다음 페이지를 가져오는 코드가 아예 없다는 것**이다.

실측 근거:
- 2026-08-14 22:31 "KIS 잔고 조회 실패 — 최다 원인 **unknown** 1회". HTTP 실패가
  아니어서 `kis.last_get_failure()`가 None이었고(=`_get`은 성공), 소비자 단계의
  '신뢰 불가' 판정으로 None이 된 경로다. 현재 원인 라벨이 이 경로를 표현하지
  못한다(P3 관측 정확도 문제도 함께 해소 대상).
- 현재 보유: KR 3 · **NASD 29** · NYSE 19 (총 51). NASD가 페이지 한도(통상
  20~30행)에 근접했다. 한도를 넘는 순간부터 **모든 잔고 조회가 상시 실패**하고,
  파수꾼은 fail-closed로 **자동 손절매도를 상시 차단**한다. 보유가 늘수록
  악화되는 구조적 시한폭탄이다.
- 이는 모의 전용 제약이 **아니다**. 실계좌 API도 동일 방식이며, 실계좌에서는
  같은 상황이 실제 자금의 보호 중단으로 이어진다.

## 2. 요구사항

### R0. (구현 전 필수 실측) 모의서버의 연속조회 지원 여부

사용자 실측 제보(2026-08-14): **KIS 모의투자 화면에서도 잔고 목록이 끝까지
스크롤되지 않는다.** 즉 모의 환경은 연속조회 자체를 지원하지 않거나 페이지
상한이 고정일 가능성이 있다. 구현 전에 Oracle에서 읽기 전용으로 확인한다:

1. 해외 잔고(NASD)를 첫 페이지 조회 → 응답의 `ctx_area_fk200`/`nk200`,
   헤더 `tr_cont` 값과 행 수를 기록.
2. 연속키가 있으면 그 값을 실어 2페이지를 요청 → `rt_cd`·`msg_cd`·행 수를 기록.
   `msg_cd=90000000`(모의 미지원) 계열이면 **모의는 연속조회 불가**로 확정.
3. 결과를 이 문서 §7에 추기한다.

**분기 A — 모의가 연속조회를 지원**: §P1을 그대로 구현.

**분기 B — 모의는 미지원(제보대로일 경우)**:
- `_get` 계층의 페이지 루프는 **live 경로용으로 구현**하되, 모의에서는
  1페이지만 조회하고 **연속키가 남으면 지금처럼 fail-closed(None)** 유지.
  절대 부분 목록으로 매매·보호 판단을 하지 않는다.
- 대신 **한도 근접 경보**를 추가한다: 거래소별 보유 종목 수가 1페이지 한도의
  80%를 넘으면 `/진단`과 텔레그램에 1회 경고("NASD 보유 29/한도 N — 초과 시
  잔고 조회 상시 실패·자동매도 차단"). 사용자가 종목 수를 관리하거나
  전환 일정을 조정할 수 있게 한다.
- 실측된 1페이지 한도(행 수)를 문서화하고, **모의 측정 기간 동안의 거래소별
  보유 상한**을 운영 파라미터로 제안한다(예: 한도−5종목). 이 상한은 매수
  게이트에 자동 반영하지 말고 **경보·문서로만** 두되, 필요 시 사용자가 승인해
  적용할 수 있게 근거 숫자를 남긴다.

### P1. 연속조회 이어받기 (핵심)

`_get` 위에 **페이지 루프 헬퍼**를 만들어 아래 조회에 적용한다:

- 해외 잔고 `overseas_balance` (NK200/FK200)
- 국내 잔고 `domestic_balance` (NK100/FK100)
- 해외 미체결 `open_orders` · 해외 체결 `fills`
- 국내 미체결/체결 계열(`domestic_open_orders`, `domestic_fills`,
  `domestic_unfilled_orders`) — 페이지 키를 쓰는 것만

동작 계약:
1. 첫 페이지는 빈 컨텍스트로 요청, 응답의 `ctx_area_fk*`·`ctx_area_nk*`를
   **그대로** 다음 요청에 싣는다(공백 트림만, 임의 가공 금지).
   연속 요청은 헤더 `tr_cont="N"`(다음 페이지)을 사용한다 — KIS 규약 확인 후
   실제 값에 맞출 것. 응답 헤더 `tr_cont`가 F/M이면 다음 페이지가 있다는 뜻이므로
   본문 키와 함께 판정에 쓴다.
2. `output1`(및 해당 조회의 행 배열)을 **누적 병합**하고, `output2`/요약은
   마지막 페이지 값을 쓴다.
3. **어느 한 페이지라도 실패**(None·`rt_cd!="0"`·형식 불신)하면 **전체를 None**으로
   반환한다 — 부분 병합 결과를 절대 반환하지 않는다(기존 fail-closed 유지).
4. **페이지 상한** `KIS_MAX_PAGES`(기본 20). 상한 도달 시에도 부분 결과를 쓰지
   않고 None + 로그. 같은 연속키가 반복되면(무한 루프 신호) 즉시 None.
5. 반환 dict에는 연속조회 키를 **남기지 않는다**(모두 소진했으므로). 그래야
   기존 소비자의 "키 있으면 불신" 계약이 그대로 통과한다 — 소비자 코드는
   원칙적으로 수정하지 않는다.
6. 유량 제한: 각 페이지는 기존 `_LIMITER`를 그대로 통과한다. 페이지 추가 호출은
   실제로 다음 페이지가 있을 때만 발생하므로 평시 비용 증가는 없다.

### P2. '성공했지만 불신' 경로의 원인 라벨링

`positions_detail`·`holdings`가 HTTP 성공 후 자체 판정으로 None을 반환할 때,
그 사유(연속페이지 미완·행 파싱 실패 등)를 `balance_health`가 읽을 수 있는
형태로 남긴다. 알림에 `unknown` 대신 구체 사유가 찍혀야 한다.
전역 단일 변수 오염을 피하도록 반환값·명시 인자 전달을 우선 검토할 것.

### P3. 회귀 안전 — 부재 증명과의 상호작용

`kis_reconcile.trusted_response_rows()`는 "연속키 없음 + 페이지 상한 미포화"를
**완전성 증명**으로 쓴다(SELL 거절 대사 R1). 페이지네이션 도입 후:
- 완전히 소진된 병합 응답은 **완전**으로 인정되어야 한다(부재 증명 가능).
- 그러나 **상한 도달·중도 실패로 만들어진 결과는 절대 완전으로 인정 금지**.
- 기존 `len(rows) >= page_limit`(15/100) 포화 휴리스틱이 병합 결과에서
  거짓 불신을 만들지 않도록 함께 조정하되, 느슨해지지 않게 할 것.

## 3. 주의

- 이 지시서는 주문 발주·kill·사이징 경로를 바꾸지 않는다. 조회 계층 전용.
- **부분 데이터 반환 금지**가 최상위 계약이다. 어떤 실패도 "적게 보이는 목록"이
  아니라 "None"으로 끝나야 한다 — 잘린 잔고는 중복매수·보호누락을 만든다.
- live/mock 분기 계약(모의 미지원 API 폴백)은 그대로 유지한다.
- 뮤테이션 검증 전 커밋(과거 실측 사고). 증거는 실패 테스트명 + 종료코드 원문.

## 4. 테스트 (최소)

1. 2페이지 응답 모의: 병합 행수 = 페이지1+페이지2, 반환 dict에 연속키 없음.
2. 3페이지 중 2번째 실패(None/rt_cd=1) → **전체 None**, 부분 병합 0.
3. 같은 연속키 반복 → None(무한 루프 차단), 호출 횟수 유한.
4. `KIS_MAX_PAGES` 도달 → None + 로그, 부분 결과 미사용.
5. 단일 페이지(연속키 없음) → 기존과 완전히 동일한 결과·호출 1회(회귀 없음).
6. `positions_detail`/`holdings`가 페이지 소진 결과로 정상 리스트 반환
   (연속키로 인한 None 소멸) + 실패 시 사유 라벨이 `unknown`이 아님.
7. `trusted_response_rows`: 소진된 병합 응답=완전 인정, 상한/중도실패 결과=불신.
8. 기존 스위트 무손상(특히 test_kis·test_sentinel·test_kis_boot·
   test_sell_reject_reconcile·test_l1_readiness·test_ops_status).
