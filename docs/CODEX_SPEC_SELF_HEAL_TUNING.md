# 구현지시서 — 자가복구 관찰 조건 완화 + 판정 관측성

작성: Claude, 2026-08-15 · 발주: 사용자 실측(12시간 미복구) 후 지시
역할: **Codex 구현 → Claude 적대 검토 → 사용자 승인 후 병합·배포**
전제: 이 문서는 **상향 규칙·L2+·operator ack 의무를 바꾸지 않는다.**

---

## 1. 문제 (2026-08-15 실측)

kill L1이 **12시간 유지**됐는데 자가복구가 한 번도 발동하지 않았다. 그 사이
`/진단`은 전부 정상이었다(heartbeat 35초, KIS 조회 성공, 원장 0/0, 서비스
전부 active, 대사 연속 실패 0). 사용자가 수동 복구했고 readiness는 전 항목 GO였다.

### 원인 가설 A — 관찰 연속성 조건이 상향 조건보다 훨씬 빡빡함

| | 기준 |
|---|---|
| 상향(watchdog) | heartbeat > **120초**(HARD_DISABLE) + 재시작 3회 소진 |
| 자가복구(kill_self_heal) | heartbeat **< 60초를 30분 연속** |

파수꾼 heartbeat는 KIS 응답 지연에 따라 늘어져 **55~59초까지 톱니처럼
출렁인다**(ops 샘플 실측: 4.6 → 21.8 → 39.0 → 55.9초). watchdog은 15초마다
관찰하므로 30분 창 안에서 **단 한 번이라도 60초를 넘으면**
`healthy_since`가 0으로 리셋되고 시계가 처음부터 다시 시작한다. KIS 타임아웃이
간헐적으로 남아 있는 한(24h 16회) 사실상 영구히 성립하지 못한다.

### 원인 가설 B — 판정 사유가 어디에도 안 남음(관측성 결함)

`infra/server/watchdog.py`는 `kill_self_heal.cycle()` 결과 중
`recovered`·`manual_alert`만 print한다. `observing`·`reset`·`blocked(why=…)`는
로그·ops 어디에도 남지 않아, 사용자가 `journalctl | grep self-heal`을 돌려도
**빈 출력**이었다. 가설 A를 로그로 확증할 수단이 없다.

## 2. 요구사항

### T1. 연속성 판정 완화 (핵심)

`bot/kill_self_heal.py`의 건강 판정을 "단발 초과로 리셋"에서
**"의미 있는 악화일 때만 리셋"** 으로 바꾼다:

- 관찰 리셋 조건: `age > SELF_HEAL_RESET_AGE_S`(기본 **90초** —
  watchdog `RESTART_AFTER_S`와 동일) **또는** 60초 초과 샘플이
  **연속 2회** 발생.
- 그 외(60~90초 단발)는 관찰을 **유지**하되 `healthy_since`는 갱신하지 않는다
  (창을 늘리지도, 리셋하지도 않음).
- 30분 창(`SELF_HEAL_OBSERVE_S`)·하루 1회 상한·L2+ 금지·readiness GO·
  화이트리스트 사유는 **그대로**.
- 근거: 상향은 120초 초과 + 재시작 3회 소진이라는 훨씬 나쁜 상태에서만
  일어난다. 복구 판정이 상향 판정보다 엄격할 이유가 없다.

### T2. 판정 관측성

- `cycle()`의 반환(action·why·observed_s·남은 시간)을 watchdog이
  **주기 로그**로 남긴다. 매 사이클(15초)마다 찍으면 소음이므로 **상태가
  바뀌었을 때 + 최소 10분에 1회**로 억제한다.
- ops 스냅샷(`bot/ops_status.py`)에 `self_heal` 오브젝트 1개 추가:
  `{"action": "...", "why": "...", "observed_s": N, "used_today": bool}`.
  심볼·금액·시크릿 없음. `/진단`에도 한 줄:
  `자가복구: 관찰 N분 · 사유 …` (L1일 때만 표시).
- readiness 호출 예외(`blocked why=readiness:XxxError`)도 위 경로로 보이게 한다.

## 3. 주의 (적대 검토 포인트)

- **완화 방향 변경이므로 "진짜 사고를 오인으로 덮는 경로"가 생기지 않아야
  한다.** 특히 heartbeat가 60~90초 사이를 계속 오가는 '만성 저하' 상태에서
  30분이 채워져 복구되는 것이 타당한지 검토할 것 — 타당하지 않다고 판단되면
  "창 내 60초 초과 샘플이 총 N회를 넘으면 리셋" 같은 총량 조건을 추가 제안하라.
- readiness GO·하루 1회·L2+ 금지·사유 화이트리스트(완전일치)는 **완화 금지**.
- ops/진단 추가 필드는 읽기 전용 계층 계약(주문·kill 변경 0)을 유지한다.
- 관찰 상태 파일 손상·쓰기 실패는 기존대로 fail-closed(복구 0건).
- 뮤테이션 검증 전 커밋. 증거는 실패 테스트명 + 종료코드 원문.

## 4. 테스트 (최소)

1. 60~90초 단발 초과가 섞여도 30분 뒤 복구 성립(T1 핵심).
2. 90초 초과 1회 → 즉시 리셋, 복구 0.
3. 60초 초과 연속 2회 → 리셋, 복구 0.
4. 만성 저하(창 내내 60~90초 반복)에서의 동작이 §3 검토 결론과 일치.
5. 상향 사유 불일치·operator 상향·L2·readiness NO-GO·하루 1회 소진은
   기존대로 복구 0(회귀).
6. 로그 억제: 상태 불변이면 10분에 1회만, 상태 변화 시 즉시 1회.
7. ops 스냅샷에 `self_heal` 필드 존재·시크릿 0, `/진단` 표기.
8. 기존 스위트 무손상(test_kill_self_heal·test_ops_status·test_kis_telegram).

## 5. 완료 기준

테스트 통과 + compileall + CI, 증거 원문. Claude 적대 검토(P0/P1=0) →
사용자 승인 → 병합. **배포 시 주의**: autodeploy 기본 재시작 목록에
watchdog이 없으므로 `sudo systemctl restart watchdog` 1회가 필요하다.
배포 후 첫 오인 L1에서 "자동 복구 1건으로 종결"을 실측하면 완료다.

## 6. T3. 외부 킥 계층 조용한 죽음 감시 (2026-08-16 추가)

### 배경 (실측)

사용자가 GitHub PAT 목록에서 **만료된 토큰**(`Stock-chart-analyze`)을 발견했다.
확인해 보니 파이프라인은 정상이었지만(15분 간격 dispatch 전부 성공,
Cloudflare 워커 `heartbeat_src="api"`), **어느 계층이 그 토큰을 쓰다가 죽었는지
아무도 알 수 없었다.** 우리 발사 계층은 3중이다:

1. GitHub 자체 크론(오프피크 :04/:19/:34/:49)
2. 외부 크론(cron-job.org, PAT — 실측상 :00/:15/:30/:45 dispatch)
3. Cloudflare 워커(PAT, 피드가 낡을 때만 발사)

이번엔 죽은 게 예비 계층이라 무해했지만, **주 계층이 조용히 죽으면 자동매매가
멈춘 걸 사람이 알아채기 전까지 아무도 모른다.** 토큰 만료는 예고 없이 온다.

### 요구사항

- 신규 스크립트 `scripts/kick_audit.py`(읽기 전용, `GITHUB_TOKEN` 사용):
  최근 24시간 워크플로 실행을 조회해 **발사 주체별 집계**를 만든다.
  - 외부 킥 = `event=workflow_dispatch` 이면서 `triggering_actor`가
    `github-actions[bot]`이 **아닌** 실행(= PAT 기반 외부 계층)
  - 내부 킥 = `schedule` 실행, 그리고 봇이 트리거한 재실행
- 판정과 경보(텔레그램, 하루 1회 억제):
  - 외부 킥 24시간 **0건** → `🚨 외부 킥 계층 24시간 무발사 — PAT 만료/크론 중단
    의심. GitHub 크론만 남음`
  - `schedule` 24시간 **0건** → `⚠️ GitHub 크론 24시간 무발화 — 외부 킥만 남음`
  - **둘 다 0건** → P0 경보(전 계층 사망 = 자동매매 정지 임박)
  - 정상이면 침묵(로그만).
- 실행 위치: 기존 `.github/workflows/watchdog.yml`(freshness-watchdog)에 스텝
  추가. 새 워크플로·새 크론을 만들지 않는다. 실패는 무해(기존 자가치유 로직에
  영향 0).
- 장 시간 판정은 필요 없다(24시간 창이므로 장외 오탐 문제 없음).

### 주의

- 이 감시는 **관측 전용**이다. 재실행·주문·kill을 건드리지 않는다.
- API 페이지네이션·rate limit을 고려해 `per_page`·`created>=` 필터로 조회량을
  제한하고, 조회 실패는 경보가 아니라 로그(거짓 경보 금지 — 조회 실패를
  "무발사"로 오독하면 안 된다. **실패 ≠ 0건** 계약은 여기서도 동일).
- 알림 문구에 토큰·시크릿·저장소 외 정보를 넣지 않는다.

### 테스트

1. 외부 킥 0 / schedule 정상 → 외부 경보 1회, P0 아님.
2. schedule 0 / 외부 정상 → 크론 경보 1회.
3. 둘 다 0 → P0 1회.
4. 둘 다 정상 → 알림 0.
5. API 조회 실패(None·HTTP 오류) → **알림 0** + 로그(실패를 0건으로 세지 않음).
6. 하루 1회 억제: 같은 판정 반복 시 재발송 0.
