# 파일 03 — Stage 2: 실행(매수/매도) + 보호(조건주문)

> 읽는 법: `##` 하나씩. **Stage 2 = 실제 돈.** 이 파일의 모든 태스크는 파일 02(주문
> primitive) + 파일 04(게이트·서버) + V2 실측 통과가 선행. 여기서 처음으로 "산다".

---

## X1 — 라이브 매수 실행기 (loop A+B의 진입 부분)

- **무엇**: 상시 서버에서 **신호 feed + 토스 시세 → 게이트/사이징 → 실제 매수주문**을
  내는 컴포넌트. 지금은 매수를 `autopaper`(GitHub, 가상)가 함 — 그걸 서버 실집행으로.
- **왜**: 파수꾼은 매도전용이라 **라이브에서 사는 주체가 아예 없다**(내 이전 리스트 최대
  누락). 주문은 깃에서 금지(§불변식4)라 매수 집행은 서버 loop여야 한다.
- **어떻게**:
  - 전략·게이트·사이징 **함수는 모의와 동일 재사용**(`scanner/gates`, `plan`, 사이징).
    바뀌는 건 입력(토스 시세·실계좌)과 출력(가상→실주문)뿐.
  - 흐름: 신호 feed(state 브랜치)에서 'now' 후보 → L5 토스가로 게이트 재확인 → X2 사이징
    → **주문 직전 단건 시세 재조회**(quote_ts 신선) + buying-power/sellable 재확인 →
    `toss_orders.place_order(side=BUY, client_order_id=...)` → O3 폴링 → 체결분으로 포지션
    기록 → **즉시 P1 보호주문 등록**.
  - 진입 상한: 쿨다운·하루 진입 ≤N·일일 −2% 서킷·종목당 1/3·MAX_POS — 모의 규칙 재사용.
- **주의**: 매수도 clientOrderId 멱등(timeout 시 이중매수 방지). **매수 체결 → 보호주문
  등록 사이의 공백**이 최대 위험(P1의 SLA). 신호 feed가 낡으면(생산 지연) 진입 보류.
- **테스트**: 후보→게이트→사이징→주문 흐름(mock broker), 멱등 재요청, 진입상한 준수,
  보호주문 미등록 시 진입 롤백/경보.
- **의존/Stage**: O1~O4, X2, P1, L3 / Stage 2.

## X2 — 라이브 사이징 (실 buying-power · 환율 · 체결가)

- **무엇**: 1% 리스크 사이징을 **실 매수여력 + 실환율 + 실체결가** 기준으로.
- **왜**: 모의는 `FX=1380` 상수·일봉종가로 계산. 실계좌는 buying-power 제약·환율 변동·
  체결 슬리피지가 있어 그대로 쓰면 리스크가 왜곡(1%가 몰래 1.4%).
- **어떻게**:
  - 수량 = min(리스크역산[= 1%×equity / 주당손절폭], 종목당1/3캡, buying-power 한도).
  - USD 종목: `GET /exchange-rate`의 `rate`로 원↔달러 환산(**validUntil ~1분** → 주문 직전
    재조회). 정수 주문(whole share, Stage 2) 우선.
  - **체결 후 재검증(actual_risk)**: `abs(avgFillPrice - stop) × filledQty > planned×1.15`
    이면 포지션 축소/청산 **검토**(즉시 강제 아님 — 경보 + 규칙).
- **주의**: buying-power(cashBuyingPower)는 미수 미발생 기준 — 예수금과 다름. 환율 만료 재조회.
  소수점은 Stage 2 금지(정수만).
- **테스트**: 리스크역산·캡·여력 세 상한 중 최솟값, 환율 반영, actual_risk 초과 감지.
- **의존/Stage**: L3, `exchange-rate`, X1 / Stage 2.

## X3 — 환전 처리 (US 매수) [실측 게이트]

- **무엇**: 미국주 매수 시 **원화→달러 환전**을 어떻게 다룰지.
- **왜**: 외화 잔고가 없으면 매수 거부될 수 있다. 자동환전 여부·시점이 스펙에 불명확.
- **어떻게**: **먼저 실측**(V2/V3) — (a) 토스가 매수 시 자동환전하나? (b) 환전 실패 시
  주문거부 코드? (c) 통합증거금? 결과에 따라: 자동환전이면 buying-power에 반영해 사이징만,
  수동환전이면 별도 환전 스텝(또는 US 매수 보류). **불명확하면 Stage 2 첫 주엔 KR만.**
- **주의**: 추정으로 환전 로직 만들지 말 것 — 실측 전엔 "US 매수 금지"가 안전 기본값.
- **테스트**: (실측 후 정의) 환전 실패→주문거부 처리, 외화잔고 부족 감지.
- **의존/Stage**: VR 실측 / Stage 2(실측 후).

## X4 — 파수꾼 실매도 (골격 채우기)

- **무엇**: `bot/sentinel.py`의 `_TossBroker.place_sell`·`order_status`(현재
  `NotImplementedError`)를 `toss_orders`로 실제 구현.
- **왜**: 파수꾼 골격(멱등키·원장·잠금·대사·quote 폴백)은 완성 — **실행부만 비어있다.**
  이걸 채우면 L2 손절(파수꾼) 실집행 완성.
- **어떻게**:
  - `place_sell(code, qty, reason, key)` → `toss_orders.place_order(side=SELL,
    order_type=MARKET|LIMIT, client_order_id=toss.client_order_id(key))` →
    응답을 `_norm_result`가 이해하는 `{state, filled}`로 반환(이미 원장 연동됨).
  - `order_status(key)` → `toss_orders.order_status(client_order_id)`의 실체결 수량 반환
    → 기존 `_reconcile_open`이 대사(이미 구현).
  - **매수 경로 없음** 유지(grep 테스트).
- **주의**: 손절은 시장가 원칙(나가는 게 우선)이나 호가공백(L6) 시 정책 분기. sellable
  상한(L6) 초과 금지. UNKNOWN이면 기존 원장 잠금 발동(이미 됨).
- **테스트**: place_sell→filled/partial/unknown 각 경로가 기존 원장·대사와 맞물림,
  매수 경로 부재.
- **의존/Stage**: O2·O3, 기존 sentinel·ledger / Stage 2.

## P1 — 조건주문 (OCO/STOP): 서버측 보호 (0차 방어, 등급화)

- **무엇**: 매수 직후 서버측 조건주문 등록 + 생명주기 관리. `POST /conditional-orders`.
- **왜**: 서버·GitHub·CF·파수꾼 **전부 죽어도** 남는 최후 손절. 단 "등록 ≠ 체결 보장"
  (GPT 최대 교정) — 등급화해서 과신 금지.
- **어떻게**:
  - **등급 판정(실측)**: SINGLE STOP + `orderType=MARKET`이 US에서 지원·체결되면 **B0a**
    (진짜 0차, 잔여위험=거래정지). 지정가만 되면 **B0b**(갭 미체결 가능=보조). 실측 전 B0b.
  - **수량 = filledQuantity 기준**(주문수량 아님 — 부분체결 대응).
  - **등록 SLA**: 매수 체결 후 5초 내 등록 시도 → 30초 내 확인 실패면 **신규진입 전면중지 +
    P0 + 파수꾼 보호모드**(강제청산 아님).
  - **expireDate 관리**: 스윙 보유(≈15거래일) > 만료면 공백 → 장전 **D-2 이하 갱신**,
    갱신(=취소후재생성) 중 공백 주의, 실패=P0.
  - **sellable 선점 정책**: 조건주문이 sellable을 예약하면 파수꾼 매도가 막힘 → 정책 A(조건
    주문 1차 신뢰, 파수꾼은 취소 후 매도) 또는 B(SINGLE MARKET STOP만, 파수꾼은 실패 시
    보조) — **실측 후 택일**. 실측 전 둘 다 켜지 않음.
  - **고아 취소**: holdings=0인데 OPEN 조건주문 → 취소(앱 수동매도 잔존). 취소 실패→잠금.
  - **Stage 2 초기 OCO profit leg 미룸** — SINGLE STOP 보호만, 익절은 파수꾼/전략.
- **주의**: 트레일 stop을 조건주문으로 매번 수정(취소후재생성)하면 공백·rate limit → **트레일은
  파수꾼 내부 stop, 서버측은 최초 구조손절만**(하루 1회/큰변동만 갱신).
- **테스트**: 등록 SLA 위반→중지, filledQty 기준 수량, 만료 갱신, 고아 취소, 등급 판정.
- **의존/Stage**: X1·L3·VR(실측) / Stage 2.

## P2 — 보호주문 커버리지 감시

- **무엇**: "지금 **모든** 라이브 포지션에 살아있는 손절(조건주문 or 파수꾼)이 있나"를
  상시 확인하는 감시자.
- **왜**: 조건주문 만료·미등록·취소·앱 개입으로 **무방비 포지션**이 조용히 생길 수 있다.
  P1의 등록 SLA는 "등록 순간"만, 이건 "지속 상태"를 본다.
- **어떻게**: 매 사이클 holdings ↔ (활성 조건주문 ∪ 파수꾼 감시목록) 대조 → 보호 없는
  포지션 발견 시 **P0 + 즉시 조건주문 재등록 시도 + 파수꾼 우선 감시**. 커버리지 지표를
  하트비트에 실어 CF 워커/대시보드가 봄.
- **주의**: 강제청산은 하지 않음(P1 원칙과 동일). 재등록 실패 반복이면 신규진입 중지 유지.
- **테스트**: 무방비 포지션 주입→P0·재등록, 커버리지 100% 시 조용.
- **의존/Stage**: P1·L3·L4 / Stage 2.
