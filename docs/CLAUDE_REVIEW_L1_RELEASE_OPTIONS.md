# Claude 검토 요청 — L1 해제 조건 분리와 단계적 매수 재개 대안

## 1. 검토 목적

이 검토의 목적은 “안전을 위해 무조건 7일 기다린다” 또는 “어제 코드가 승인됐으니
즉시 L1을 내린다” 중 하나를 근거 없이 선택하지 않는 것이다. 현재 하나로 묶인
L1 하향 조건을 실제 의존 기능별로 분리하고, 신규매수에 꼭 필요한 조건만 충족한
상태에서 더 작은 범위로 재개할 방법이 있는지 코드와 반례로 판정해 달라.

이번 요청은 **읽기 전용 설계 검토**다. 검토 과정에서 PR 병합, Oracle 배포,
환경변수 변경, kill-switch 하향, 동결 해제, 주문 전송을 수행하지 말아 달라.

## 3. 마지막으로 문서화된 완료 상태

- KIS 환경 `mock`
- kill-switch L1: `buy_new=False`, `protect_sell=True`
- legacy BUY 16건 이관 완료
- 모든 legacy BUY `accounted == original_qty`
- 과거 SELL 10건 `filled`, `accounted == sold_qty`
- 브로커 보유수량 = `kis_positions` 수량 = costbook 수량
- 주문 원장과 costbook 정상
- 열린 주문 0건
- 총시드 35,000,000원
- 5% 완충 후 운영한도 33,250,000원
- 마지막 기록의 장부 운용원가 26,214,776.70원
- Oracle signal fallback 비활성(`ORACLE_SIGNAL_FALLBACK_ENABLED=0`)
- 정체청산 `STALL_EXIT_MODE=shadow`
- AQN, CAG, GPK, LW, SNN, VRSK는 close-only 동결 유지

위 완료 항목은 코드 승인과 회계 이관 결과다. “L1 하향 승인”과 동일한 의미로
기록돼 있지는 않다.

## 4. 현재 하나로 묶여 있는 미완료 조건

PR #96과 인수인계서는 다음 조건을 모두 마친 뒤 L1 하향을 검토하도록 기록한다.

1. 미국 정규장 관리 사이클에서 9종목의 durable `half_done=true`,
   `stop >= entry` 확인
2. 정체청산 `shadow` 최소 7일 관찰
3. oracle-brain 한국·미국 각 1세션 관찰
4. L1 상태에서 GitHub 60분 장애주입, 신규주문 0건 확인
5. close-only 동결 6종목 유지 또는 해제 결정
6. 최신 브로커·원장·예산·heartbeat 재검증
7. 사용자 승인과 운영자 ack

핵심 질문은 1~5가 모두 **일반 GitHub 신호의 mock 신규매수 재개**에 필요한지,
아니면 일부가 정체청산 `live`, Oracle fallback 활성화, 동결 종목 재매수처럼
서로 다른 기능의 승인 조건인지다.

## 5. 반드시 코드로 확인할 결합 관계

다음 표의 “검토 판정”을 `필수`, `조건부`, `별도 기능 조건`, `불필요` 중 하나로
채우고 근거 파일·함수·테스트를 적어 달라.

| 조건 | 현재 연결된 기능 | 검토 판정 | 근거와 실패 시 결과 |
|---|---|---|---|
| mock 환경 | 모든 신규주문 |  |  |
| 주문 원장 정상·UNKNOWN 0 | 모든 신규주문 |  |  |
| 열린 주문 0 | L1 하향 시점 |  |  |
| 브로커·보호원장·costbook 수량 일치 | 모든 신규주문 |  |  |
| 운용원가 ≤ 33,250,000원 | 모든 신규주문 |  |  |
| sentinel heartbeat 정상 | 모든 신규주문 |  |  |
| 9종목 `half_done`·본전 보호선 | 기존 보유 관리 |  |  |
| 정체청산 shadow 7일 | `STALL_EXIT_MODE=live` |  |  |
| oracle-brain 한·미 세션 | Oracle fallback |  |  |
| GitHub 60분 장애주입 | Oracle fallback 또는 GitHub fail-closed |  |  |
| 동결 6종목 결정 | 해당 6종목 재매수 |  |  |
| 사용자 승인·운영자 ack | kill-switch 하향 |  |  |

특히 아래 세 가설을 소스와 테스트로 반증하거나 확인해 달라.

1. `STALL_EXIT_MODE=shadow`는 정체청산 주문과 추가 래칫을 0건으로 유지하므로,
   shadow 7일은 `live` 전환 조건이지 기존 청산 규칙을 유지한 L0 신규매수의
   필수조건이 아닐 수 있다.
2. `ORACLE_SIGNAL_FALLBACK_ENABLED=0`이면 oracle-brain 결과는 매수 입력으로
   선택되지 않고, GitHub 피드까지 낡으면 신호 0건으로 실패하므로 한·미 세션
   관찰과 60분 장애주입은 fallback 1의 조건이지 L0의 필수조건이 아닐 수 있다.
3. close-only 동결은 `ownership.buy_denied()`에서 해당 심볼만 매수 거부하므로,
   6종목을 계속 동결한 채 다른 명시적 allowlist 종목만 재개할 수 있다.

## 6. 현재 코드에서 발견한 카나리 재개의 제약

아래 내용은 대안이 이미 안전하게 구현됐다는 주장이 아니라, Claude가 직접
재현해야 할 검토 포인트다.

### 6.1 기존 포지션 수와 Stage 상한

마지막 기록의 보호원장 포지션은 총 16종목이지만, 이 문서 작성 컴퓨터에서는
현재 A/B 귀속별 개수를 실측하지 못했다. `bot/rollout.py`의 상한은 다음과 같다.

- Stage 1.5: 동시 1종목, 하루 1건, risk 0.1%, allowlist 필수
- Stage 3: 동시 5종목, 하루 3건, risk 1%
- mirror: 동시 12종목, 하루 10건, risk 1%, allowlist 선택

`bot/kis_buyloop.py`는 브로커 보유와 예약에서 슬리브별 `n_open`을 계산해
`rollout.check_new_entry()`에 전달한다. 16종목이 실제로 모두 A라면 L1을 L0으로
내려도 Stage 1.5·3·mirror 모두 A 신규매수를 포지션 상한에서 차단할 가능성이
높다. 반면 B 슬리브의 현재 포지션 수가 0이라면 B 후보는 통과할 가능성이 있으므로,
Oracle에서 A/B별 현재 개수를 확인한 뒤 L0이 실제로 어느 슬리브를 여는지
판정해야 한다.

### 6.2 Stage 1.5 risk 값 불일치 가능성

`kis_buy.execute_entry()`의 기본 `risk_pct`는 `envelope.DEFAULT_RISK_PCT=0.01`
(1%)다. 현재 `kis_buyloop.run_once()`는 `risk_pct`를 별도로 전달하지 않는다.
Stage 1.5 상한은 `0.001`(0.1%)이므로 단순히 `TRADE_STAGE=1.5`로 바꾸면 모든
신규매수가 risk 게이트에서 차단될 수 있다.

카나리 재개안에 Stage 1.5를 사용하려면 다음 중 무엇이 맞는지 판정해 달라.

- Stage profile의 `risk_cap`을 실제 사이징 `risk_pct`로 전달
- 별도 명시적 `KIS_RISK_PCT`를 도입하고 Stage cap 이하로 제한
- 현재 불일치를 의도된 전면차단으로 보고 Stage 1.5를 사용하지 않음

어느 안이든 주문 전송 전에 단위테스트와 통합테스트가 필요하다.

## 7. 비교할 대안

### 대안 A — 기존 계획 유지

L1을 유지하고 shadow 7일, Oracle 한·미 세션, GitHub 60분 장애, 동결 결정까지
모두 완료한 뒤 PR #97의 읽기 전용 점검을 통과하고 L0으로 내린다.

판정할 내용:

- 가장 보수적인 대신, 서로 독립적인 기능의 관찰을 L0에 과도하게 결합했는가?
- 7일 동안 신규매수를 막아 얻는 추가 안전 증거가 구체적으로 무엇인가?

### 대안 B — 기능별 승인 분리 후 제한적 L0

다음 조건을 유지한 채 일반 GitHub 신호의 mock 신규매수만 재개한다.

- `STALL_EXIT_MODE=shadow` 유지
- `ORACLE_SIGNAL_FALLBACK_ENABLED=0` 유지
- 6종목 close-only 동결 유지
- 실전 하드블록 유지
- 브로커·원장·예산·heartbeat·열린 주문 핵심 게이트는 즉시 재검증
- allowlist와 하루 신규 한도를 강제

판정할 내용:

- shadow·fallback·동결이 실제로 위 범위 밖 주문을 코드에서 차단하는가?
- L0이 열어 버리는 다른 경로가 있는가?
- Oracle 실측에서 A가 각 Stage 상한 이상이면 A는 막히고 B만 열릴 가능성이 있는가?

### 대안 C — 한 종목·한 주문 카나리 후 자동 L1 복귀

코드와 설정을 보완해 mock 정규장 한 세션 동안 다음만 허용한다.

- 명시적 allowlist 1종목
- 최대 신규주문 1건
- risk 0.1% 이하
- 주문 ACK 또는 제한시간 도달 즉시 kill-switch를 다시 L1로 상향
- UNKNOWN, 원장 손상, heartbeat 60초 초과, 예산 불일치가 발생하면 즉시 L1 상향

판정할 내용:

- 기존 kill-switch를 우회하지 않고 구현할 수 있는가?
- 자동 L1 복귀가 프로세스 재시작·부분체결·주문 타임아웃에도 멱등인가?
- ACK 직후 L1 복귀가 pending 주문 관리와 보호매도를 방해하지 않는가?
- Stage 1.5 risk 불일치와 기존 포지션 상한을 어떻게 해결해야 하는가?
- 현재 `heartbeat.entry_allowed()`는 120초까지 허용하므로 카나리의 60초 기준을
  쓰려면 별도 코드가 필요한가?

### 대안 D — L1 유지 상태의 예외 주문

특정 종목 한 건만 kill-switch 밖에서 예외 처리하거나 수동 스크립트로 주문한다.

이 안은 kill-switch 단일 진실을 깨뜨릴 가능성이 높다. 안전한 증명이 불가능하면
명확히 `기각`으로 판정해 달라. 단지 주문 수가 한 건이라는 이유로 승인하지 말아
달라.

### 대안 E — L0 하향 후 `ALLOW_BUY=0` 유지

kill-switch만 L0으로 내리고 `ALLOW_BUY=0`으로 주문 경로는 계속 봉인한 뒤,
상태와 모니터링을 확인하고 별도 단계에서 `ALLOW_BUY=1`을 적용한다.

판정할 내용:

- 이 방식이 실제 안전 검증을 추가하는가, 아니면 상태만 복잡하게 만드는가?
- kill-switch와 환경변수 사이의 운영 상태 불일치가 장애 대응을 더 어렵게 하는가?

## 8. 반드시 실행하거나 추가할 반례

1. L0 + fallback 0 + GitHub stale/invalid → 신규주문 0
2. L0 + stall shadow → 정체청산 주문 0, shadow 전용 상태 외 추가 래칫 0
3. L0 + 동결 6종목 → 해당 6종목 신규매수 0
4. L0 + allowlist 1종목 → 목록 밖 신규매수 0
5. L0 + 브로커 A 포지션 16개 + mirror → A 신규매수 0
6. L0 + B 포지션 0개 → B가 열리는지, 열린다면 어떤 추가 게이트가 필요한지 확인
7. Stage 1.5 + 기본 `risk_pct=1%` → risk cap에서 차단되는지 확인
8. Stage 1.5에서 risk 0.1%를 실제 사이징까지 전달했을 때 수량·총시드 상한 확인
9. ACK 후 자동 L1 복귀 중 부분체결·UNKNOWN → 중복주문과 초과매도 0
10. 현금 부족·매수여력 조회 실패 → 수량 0, 주문 0
11. heartbeat 61~120초에서 현재 코드는 진입을 허용하는지 확인하고, 카나리
    60초 기준을 채택한다면 신규주문 0으로 만드는 회귀 테스트 추가
12. heartbeat 파일 손상 또는 120초 초과 → 신규주문 0
13. 브로커·`kis_positions`·costbook 수량 하나라도 불일치 → 신규주문 0

실제 KIS 호출이 필요 없는 반례는 mock으로 실행하고, Oracle 실측이 필요한 항목은
“환경 검증 대기”로 분리해 달라. 테스트 통과를 운영 관찰 완료로 바꾸어 쓰지 말아
달라.

다음 순서로 답해 달라.

1. **최종 판정:** `L1 유지`, `조건부 카나리 허용`, `제한적 L0 허용` 중 하나
2. **승인 범위 확인:** 어제 승인이 포함한 것과 포함하지 않은 것
3. **게이트 분류표:** §5 표를 완성
4. **P0/P1/P2/P3 발견사항:** 파일·함수·반례와 함께 제시
5. **대안 비교:** A~E의 위험, 장점, 기각 사유
6. **추천 실행 순서:** 준비 → 검증 → 변경 → 관찰 → rollback
7. **필요한 코드 변경:** 없으면 `없음`, 있으면 최소 diff 단위로 명시
8. **필요한 운영 증거:** 자동 생성 증거와 사람 결정 항목을 분리
9. **최종 승인 문구 예시:** 사용자가 실제로 승인해야 할 범위를 한 문장으로 제시

일반론이나 “조심해서 진행”이라는 표현만으로 끝내지 말고, 현재 코드에서 주문이
열리는 정확한 경로와 닫히는 정확한 게이트를 근거로 판정해 달라.
