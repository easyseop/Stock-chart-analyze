## P1-1. 원인 교대 시 경보 억제 무력화 (`bot/balance_health.py`)

`record_failure`는 `_incident["cause"] != cause`면 사건을 새로 시작한다.
실제 플래핑에서 흔한 "타임아웃 ↔ HTTP 500 교대"를 주입하면:

```
교대 원인 10회(30초 간격) → 경보 10건   ← 검토자 프로브 실측
```

즉 8/11 15시대 폭주(22분 8회)와 같은 상황에서 원인 라벨만 섞이면 H1 억제가
**전혀 작동하지 않는다** — 이 지시서의 존재 이유가 핵심 시나리오에서 실패.

**수정 요구**: 사건(incident)은 "잔고 조회 실패"라는 사실로 하나만 유지하고
원인 변경은 사건 리셋이 아니라 사건 내 통계(Counter)로 누적하라. 알림 문구에
최다 원인·원인 가짓수를 표기하면 정보 손실도 없다. 회귀 테스트: 교대 원인
10회 → 경보 1건(첫) + 30분 후 1건 규칙이 유지될 것.

## P2-1. 하향 직전 크래시 잔재가 거짓 "자동 L0 복구" 알림을 낸다

`kill_self_heal.cycle`은 `used=True`·`pending_notice`를 저장한 **뒤에**
`lower_level`을 호출한다. 그 사이 크래시하면 하향은 안 됐는데 pending이
남고, 이후 **수동으로** L0가 되는 순간(며칠 뒤라도 — 날짜 리셋이 pending을
보존) 자동 복구 알림이 그대로 나간다. 검토자 프로브로 재현:

```
cycle 결과: {'action': 'notice_delivered'}
발송: ['✅ kill-switch 자동 L0 복구 — …']   ← 실제 하향 주체는 수동
```

매매 영향은 없지만 kill 전환의 귀속을 속이는 알림이다(검토요청 Q10의 답이
"나간다"임). **수정**: pending 전달 전에 `kill.status()`의 who가
`self-heal`인지 확인하고, 아니면 pending을 폐기하고 로그만 남겨라.

## P2-2. 사유 화이트리스트 완전일치 계약이 무시험 (M-S1 생존)

`self_heal_allowed`를 접두 10자 일치로 약화해도 `test_kill_self_heal`이
전부 통과한다. 정책상 가장 중요한 기본 거부 계약이 리팩터에 무방비.
**수정**: 변형 사유(접두·부분·공백/대소문자 변형)가 전부 거부되는 회귀
테스트 추가.

## P3 (비차단)

1. `kis._LAST_GET_FAILURE`는 모듈 전역이라 ops 데몬 스레드와 sentinel이
   동시에 조회하면 원인 라벨이 교차 오염될 수 있다(관측 정확도만 영향).
   스레드로컬 또는 반환값 전달 구조가 더 정확하다.
2. sentinel 첫 실패 경보에서 기존 "마지막 정상 잔고 N초 전 스냅샷" 정보가
   사라졌다 — 캐시 신선도는 fail-closed 판단에 유용한 문맥이라 문구에 복원
   권장.
3. `record_failure`가 실패마다 상태파일을 fsync 기록 — 플래핑 중 15초마다
   디스크 쓰기. 무해하나 요약 갱신은 억제 창 단위로 충분.
