## 2. 근본 원인(구조)

`bot/alpha.py:nav_inputs()`는 한 관측점을 이렇게 만든다.

```python
value = (broker_bucket["cost"] + broker_bucket["pl"]) * fx   # 브로커 실시간
flow  = costbook.market_totals(...)["buy_cost"] - [...]["sell_proceeds"]  # 로컬 원장
```

그리고 `_twr_step()`이 두 소스를 빼서 구간수익률을 만든다.

```python
interval = (cur_value - old_value - (cur_flow - old_flow)) / old_value
```

**두 소스의 갱신 시점이 다르면 그 차이가 통째로 손익이 된다.** 매도는 유령
손실, 매수는 유령 이익이 된다. 한 번 곱해진 값은 `wealth`에 남아 세션 내내
유지되고, `_close_alert`가 `days[]`에 넣으면 1개월·3개월·전체까지 오염된다.

종전 가드는 이것뿐이었다.

```python
if interval > -1 and abs(interval) < 5:      # 한 틱 500%까지 통과
```

`-99.5%`도, `+400%`도 그대로 누적됐다. 사실상 무방비다.

### 3.1 `c3ab0d76` — 회계 지연 경로 (선행 수정)

  회계가 붙은 뒤 원래 기준선에서 한 번에 계산하면 평가액 변화와 외부흐름이
  같은 구간에서 상쇄된다(수학적으로 정확히 0).

### 3.2 `e926a468` — 구간 자체 검증 (본 수정)

- **한 틱 변동 한계**: 장중 `3%`, 세션 첫 갭 `10%`
  (`ALPHA_MAX_TICK_MOVE`/`ALPHA_MAX_GAP_MOVE`로 조정).
  초과 시 **원인 불문** 누적 보류 + 기준선 유지 → 시차면 자동 해소.
- **영구 동결 방지**: 보류가 `_ANOMALY_HOLD_TICKS`(3틱, 약 15분)를 넘으면
  시차가 아닌 실제 변화로 보고 **기준선만 옮긴다**. 그 점프는 누적하지 않는다
  (없는 손익을 만들지 않는다). 대신 표시가 과소해질 수 있어 경보한다.
- **사후 진단 가능화**: 이상 구간의 `prev/cur value·flow` 원본을
  `day["anomaly_log"]`에 남긴다(최대 20건). 08-04에 이게 없어서 원인 특정에
  실패했다.
- **자동 감지**: 세션당 1회 텔레그램 경보. 종전엔 사람이 차트를 보고 발견했다.
- **누적 보호**: 이상 미해소로 마감한 날은 `days[]` 제외.
- `scripts/alpha_reanchor.py`: 이미 오염된 진행 세션의 기준점을 **계좌·지수

## 5. Claude의 자기비판 — 검토자가 집중해서 반박해 주기 바라는 부분

1. **한계값 3%가 임의적이다.** 다종목 계좌가 5분에 3% 움직이는 일이 실질적으로
   없다는 것은 관찰에 근거한 판단이지 증명이 아니다. 폭락장·서킷브레이커·
   단일종목 집중 상태에서 정상 데이터가 억눌릴 수 있다. `_ANOMALY_HOLD_TICKS`로
   15분 뒤 재기준되게 완화했지만, **그 15분의 실제 등락은 기록에서 사라진다.**
   → 반례: 보유가 3종목뿐이고 하나가 -30% 갭하락하면? 계좌 -10%는 진짜인데
     보류됐다가 기준선만 옮겨져 **실제 손실이 성과에 안 남는다.**
2. **과소보고를 선택했다.** "없는 손익을 만들지 않는다"를 "실제 손익을 놓칠 수
   있다"보다 우선했다. 이 우선순위 자체가 옳은지 검토가 필요하다. 특히 실전
   전환 후에는 손실 과소표시가 위험할 수 있다.
3. **08-04 절벽의 원인을 여전히 모른다.** 구조 방어로 증상은 막았지만 원인은
   미상이다. `anomaly_log`가 다음 발생 때 원인을 잡아줄 것이라는 가정에 기대고
   있다. 그 가정이 맞는지(남기는 필드가 충분한지) 검토 바란다.
4. **`nav_inputs`의 두 소스 문제 자체는 손대지 않았다.** 근본 해법은 평가액과
   현금흐름을 같은 순간·같은 원장에서 읽는 것이다. 이번 수정은 그 위에 얹은
   검증층이며, 소스 통일은 하지 않았다. 이게 충분한지 판단 바란다.
5. **매수 사건의 재발 방지가 없다.** kill CLI와 감사로그는 고쳤지만,
   "게이트가 조용히 막고 있는 상태를 사람이 5일 뒤에 발견"하는 구조는 그대로다.
   `l1_readiness`에 kill 레벨 게이트가 있지만 **아무도 주기적으로 돌리지 않는다.**
   → 제안 검토 요망: buyloop이 "N사이클 연속 모든 후보가 같은 게이트에서
     차단됨"을 감지해 경보하는 것.
6. **`_twr_step`이 두 번 순회한다.** 첫 순회에서 interval을 모으고 둘째에서
   적용한다. 가독성·성능은 무해하나, 두 순회 사이에 `nav`가 바뀌지 않는다는
   가정이 코드로 강제되지 않는다.

## 6. 검토자가 확인해 줄 것

- §5의 6개 항목 각각에 대해 **실제 반례를 구성**해 재현되는지.
- 한계값 3%/10%/3틱이 이 계좌 규모·종목 수에서 타당한지, 더 나은 기준이 있는지.
- `_twr_step`의 보류→재기준 전이에서 `nav_last`/`carry`가 어긋나 **다음 날**
  기준선이 틀어지는 경로가 있는지.
- `alpha_reanchor.py`가 `carry`를 지우는 것이 다른 시장(KR)이나 다음 세션에
  부작용을 만드는지.
- kill CLI `parse_known_args` 변경이 기존 문서 명령·자동화 스크립트를 깨지
  않는지.
- 이 수정들이 **주문 경로에 어떤 영향도 주지 않는지**(alpha는 보고 전용이어야
  한다). `alpha.tick()` 실패가 매매를 막지 않는지 확인 바란다.
