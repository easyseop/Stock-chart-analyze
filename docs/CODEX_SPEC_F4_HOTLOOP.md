## G1 (P1-1, 차단) — F4의 조회 6회가 heartbeat를 갉아먹는다

### 실측

감사 1회가 부르는 KIS 호출(US 개장 시):

```
balance NASD · nccs NASD · balance NYSE · nccs NYSE · balance AMEX · nccs AMEX = 6회
```

호출당 3초만 가정해도 감사 소요 **18.0초**(검토자 실측). `bot/kis.py:_get`은
`for attempt in range(3)`이고 각 attempt가 `유량대기 10s + HTTP 15s`라
**호출당 최악 75초 · 6회면 450초**다.

그 구간에 heartbeat 갱신이 **없다**. `protection_observability`는 heartbeat를
전혀 참조하지 않고(`grep` 0건), `sentinel.py`는 감사 직전에 `_beat`를 한 번
찍을 뿐이다. 감사 소요분이 heartbeat 나이에 그대로 더해진다.

```
AGE_OK_S = 30 · AGE_P0_S = 60 · AGE_HARD_S = 120 → HARD_DISABLE → kill L1 상향
```

### 왜 차단인가

지연이 커지는 조건이 **KIS 응답 저하**인데, 그건 heartbeat가 이미 눌려 있는
바로 그 순간이다. 2026-08-21의 25분짜리 `TimeoutError` 장애가 그 상황이었고
그 사고 때문에 만든 것이 지금의 watchdog 장애 분류다. 관측성 기능이 자기가
관측하려던 사고를 유발하는 구조는 방향이 틀렸다.

읽기 전용이고 예외 격리도 돼 있지만 **예외가 아니라 지연**이라 `try/except`로
막히지 않는다. F3(원장만 읽음)은 무관하고 **F4만** 해당한다.

### 요구사항 — 아래 중 택1 (①을 권장)

**① 핫루프 밖으로 옮긴다.** `ops_status`가 이미 주기 점검 루프를 갖고 있고
손절 판단과 무관한 프로세스다. F4를 거기서 돌린다. `sentinel.py`에서는 F4
호출을 제거하고 **F3만 남긴다**(F3는 원장만 읽어 지연이 없다).

**② 데드라인으로 감싼다.** 파수꾼에 남기되 감사 전체에 상한(기본 10초,
env 조정 가능)을 건다. 초과하면 그 사이클을 **버리고** 다음 주기에 재시도한다.
`bot/ops_status.py:_call_before_deadline`이 이미 같은 일을 하니 재사용하라 —
새로 만들지 말 것. 부분 결과로 판정하면 안 된다(초과 = 판정 보류 = 래치 유지).

②를 고르면 데드라인 초과가 `_collect_sellable_snapshot`의 `None`과 **같은
경로**로 흘러야 한다. 즉 경보 0·회복 0·래치 불변이다.

### 하지 말 것

- F1·F2·F3 로직을 건드리지 말 것. 검증이 끝났다.
- 거래소 사이에 `_beat`만 추가하는 해법은 **불충분**하다. 호출 하나가 최악
  75초라 beat 간격이 여전히 `AGE_HARD_S`를 넘길 수 있다.
- `_get`의 재시도·타임아웃·유량 설정을 바꾸지 말 것. 그건 주문 경로가 공유한다.
- F4의 판정식·래치·정화는 그대로 둘 것(검토 통과).

### 회귀 테스트 (필수)

1. ①을 골랐다면: `sentinel.check_once`가 어떤 경로로도 `audit_sellable_gaps`를
   호출하지 않음(spy 0회). F3는 계속 호출됨.
2. ②를 골랐다면: 조회가 데드라인을 넘기면 경보 0·회복 0·래치 파일 **바이트
   동일**, 반환은 `None` 경로와 구분 불가.
3. ②를 골랐다면: 정상 소요(데드라인 이내)에서는 기존 판정이 그대로 나옴
   (11/1/open0 → 경보, 11/6/open5 → 침묵).
4. 어느 쪽이든: 파수꾼 사이클에서 F4가 유발하는 블로킹 호출 수가 0(①) 또는
   데드라인 상한 이내(②)임을 호출 spy로 고정.

## G2 (P3-1) — `side == "SELL"` 제한이 또 미테스트

`operator-zero-fill`에서 `side == "SELL"`을 제거한 뮤턴트가 검토자 실행에서
**SURVIVED**했다. 실측하면 BUY(0체결행·나머지 조건 충족)도
`operator-zero-fill`이 된다. 현재 코드는 정상이다(BUY → `hold` 확인).

**직전 라운드 P3-1과 같은 항목이 새 분기에 그대로 재발했다.** 비대칭도 그대로다
— BUY 오종결은 원장에 없는 보유를 만들어 손절 기록조차 없는 포지션이 되고,
SELL 오종결은 발주 클램프가 흡수한다.

테스트 1건: BUY + ccnl 단일 0체결행 + 나머지 조건 충족 → `kind == "hold"`.

## G3 (P3-2) — 일시 예약 오탐 가드

서버 실측으로 가장 그럴듯했던 오탐 경로는 배제됐다:

```
PEP  총보유 16 · 매도가능 16      (8/21 매수분, 다음 날 조회)
```

매수분이 결제 미도래로 빠지지 않는다. 다만 표본 1건이고 **매수 당일 장중**은
미관측이며, 대차·증거금 등 다른 비주문 예약도 확인되지 않았다.

값싼 보험을 둔다: **연속 N회(기본 2, env 조정) 같은 갭이 유지될 때만** P0.
일시 예약은 다음 사이클에 풀리고 INGR 같은 영구 누수만 남는다. 카운터는 기존
래치 파일에 같이 영속하고, 갭이 사라지면 카운터도 리셋한다.

테스트: 1회차 침묵 → 2회차 경보 → 중간에 갭 해소되면 카운터 리셋 후 재시작.

## 지켜야 할 불변식

1. 발주 클램프 `safe_qty = min(요청, 매도가능)` 약화 0.
2. 사용자 baseline denylist 완화 0.
3. kill-switch·손절 발주 경로 diff 0.
4. 동결 자동 해제 0 — 해제는 운영자 ack만.
5. `실패 ≠ 부재` — 조회 실패·데드라인 초과 모두 판정 보류·래치 유지.
6. 공개 ntfy category-only.
7. F4는 어떤 경우에도 손절 판단을 **지연시키지 않는다**.
