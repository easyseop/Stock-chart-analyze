# 신뢰성 종합 분석 — "깃액션이 자꾸 죽는" 문제와 실거래 무리스크 운영안

> 2026-07-08 작성 · **v2 (2차 SRE 검토 반영)**. 2주 운영(사건 16건) 실측 기반 결정 문서.
> 결론 요약: **고장 나는 것은 GitHub이 아니라 '무료 크론의 정시성'이다.
> 정시성이 필요한 경로(가격→매매→손절)를 계층별로 분리해, 각 계층에
> 맞는 인프라를 배정한다. 목표는 "단일 인프라 장애(GitHub/CF/텔레그램)가
> 직접 손절 불능으로 이어지지 않게 하는 것"** — 그 경우 피해는 신규 진입
> 공백(기회비용)으로 격하된다. 단, **파수꾼↔브로커 경계 장애**(인증 만료·
> 주문 UNKNOWN·부분체결·시세 지연·기업행위)에서는 여전히 손절 불능/원치
> 않는 매도가 가능하므로 §Phase B의 별도 방어가 필수다(2차 검토 §5 반영).

**근본 원인 한 줄**: 무료 GitHub 크론은 "정시 실행을 보장하지 않는 것이 계약 조건"인데,
우리 시스템의 심장(가격 갱신→자동매매)이 그 정시성에 얹혀 있다.

**이미 작동 중인 방어** (이번 주에 실증됨):
cron-job.org 외부 킥(오늘 시스템을 실질 가동한 주력) · 워치독 자가치유 ·
오프피크 크론 · guard 공회전 방지 · state 브랜치 계좌 백업 · 전 실패 경로 텔레그램.
→ **덕분에 "계좌 손상"은 지금까지 0건.** 남은 문제는 "지연"이지 "손실"이 아니다.

## 2. 설계 원칙 — 정시성 요구로 계층을 나눈다

같은 시스템 안에 정시성 요구가 전혀 다른 세 가지 일이 섞여 있다. 분리가 답이다.

| 계층 | 일 | 정시성 요구 | 맞는 인프라 |
|---|---|---|---|
| L1 분석·렌더 | 5,400종목 스캔, 900MB 페이지 | 낮음(수십 분 늦어도 무해) | GitHub Actions (무료 무제한, 지금처럼) |
| L2 **가격→매매 스텝** | 보유·후보 시세 + 자동매매 1스텝 + 피드 | **중간(15분 보장)** | GitHub Actions 실행 + **보장된 외부 발사·검증** |
| L3 **손절 집행** (실거래) | 보유 종목 손절선 감시·매도 | **높음(초 단위, 항상)** | **상주 프로세스** — GitHub으론 불가능, 별도 호스트 |

핵심 통찰: L2를 L1에서 떼어내면(빠른 모드) 오늘 같은 렌더 정체(F4)가 매매를 못 막고,
L3를 GitHub 밖에 두면(파수꾼 — 이미 dry-run 완성) **GitHub 전면 장애조차 손실로
이어지지 않는다.** 이 두 분리가 전체 계획의 뼈대다.

## 3. 로드맵 — 3단계 (비용 0~5$/월)

### Phase A — 지금(모의 단계) 바로: "지연"을 구조적으로 줄인다

| # | 항목 | 해결하는 고장 | 작업 |
|---|---|---|---|
| A1 | **빠른 모드(fast) 분리** — 보유·대기·후보 시세 + autopaper + 피드만 갱신(~3분), 페이지 렌더·배포 생략. **⚠ 필수 동반: 매매 스텝 state lock**(fast/bulk 차선이 분리되는 순간 이중 매매 위험(F8) — 매매 스텝의 단일 쓰기 소유권을 코드로 강제) | F4 (렌더가 매매를 막는 구조) | 코드(클로드) |
| A2 | **Cloudflare Worker 크론** — GitHub과 **독립된 외부 발사·검증 계층**(정시 '보장'이 아니라 15분 슬롯마다 **생성→시작→성공→하트비트**를 검증하고 미달 시 재시도·경보). 무료 10만 요청/일 중 ~200/일 사용 | F1·F2·**F7** | Worker 코드(클로드) + CF 계정 연결(사용자 ~20분) |
| A3 | **종목별 신선도 스탬프 + 무음 정지 경보** — 데이터 나이가 임계 초과한 보유/추천 종목은 강제 재수집, 반복 실패 시 텔레그램 | F5 (TSLA류 무음 동결) | 코드(클로드) |
| A4 | **운영 규율의 코드화** — 전체 재렌더(BUILD_SHA 변경)는 장중이면 다음 장외로 지연 | F4 재발 방지 | 코드(클로드) |

Phase A 후 상태: 발사는 CF가 보장, 매매 경로는 3분짜리 경량이라 밀릴 일이 없고,
종목 동결은 자동 감지·회복. **cron-job.org는 2차 백업으로 유지**(이중 발사는 guard가 걸러냄).

### Phase B — 실거래 결정 시: "단일 인프라 장애 ≠ 손절 불능" 보장

| # | 항목 | 근거 |
|---|---|---|
| **B0** | **브로커 서버측 stop/조건주문** — 지원되면 **매수 직후 반드시 등록**. GitHub·CF·파수꾼이 동시에 죽어도 브로커에 남는 **1차(최후) 방어선**. 미지원이면 파수꾼 중요도가 급상승 → micro live 기간·규모를 더 보수적으로 | 2차 검토 §12 — 방어 서열: ①브로커 stop ②파수꾼 ③GitHub 15분 ④P0 수동 |
| B1 | **파수꾼(sentinel) 상주 가동** — Oracle Cloud 무료 티어 또는 $5 VPS. 손절 전담(매수 경로 없음 — 코드 grep 테스트 + **가능하면 브로커 API 키 자체를 조회+매도 전용 발급**) | L3 분리 — STRATEGY 5.5.1, 코드 완성·dry-run 검증 끝 |
| B2 | **주문 원장 + 부분체결 reconcile + 포지션 정체성 멱등키** | SRE 재검토 지적 — 스펙 주석으로 이미 고정(sentinel.py) |
| B3 | **concurrency 전용 그룹 + state lock** — 같은 주문 이중 발사 차단 | 현재 pages 그룹 직렬화 → 전용 승격 |
| B4 | **P0 경보 ntfy 이중화** — 텔레그램 죽어도 매매정지·위반·파수꾼 사망은 도달 | 남은 유일한 경보 단일점 |
| B5 | **CF Worker가 파수꾼 하트비트 감시** (감시의 감시) — 파수꾼 무응답 N분 → P0 | 데드맨 스위치를 GitHub 밖에 |

### Phase C — 실거래 안정화 후

- 브로커 실보유 ↔ 내부 상태 자동 대사(일 1회) · 슬리피지 계측 리포트
- (선택) 전략·계좌 비공개화 — 공개 러너 + 비공개 브레인 분리

## 4. "리스크 없이"의 정확한 의미 — 실거래 장애 매트릭스

Phase A+B 완료 상태에서 각 장애가 돈에 미치는 영향:

| 장애 시나리오 | 신규 진입 | **보유 손절** | 계좌 기록 | 결론 |
|---|---|---|---|---|
| GitHub 크론 드랍(F1) | CF가 발사 — 정상 | 브로커 stop+파수꾼 정상 | 정상 | 영향 없음 |
| GitHub Actions 전면 장애(F2) | **공백** (기회비용) | **브로커 stop·파수꾼·주문원장이 정상일 때** 계속 집행 | state 브랜치 보존 | 기본 영향은 진입 공백 |
| CF Worker 장애 | GitHub 크론+cron-job 백업 발사 | 무관 | 정상 | 지연만 |
| 파수꾼 호스트 사망 | 신규 진입 금지 flag | ⚠️ **브로커 서버측 stop이 1차 방어**(B0), 15분 폴링 강등 + **P0 즉시**(B5 — GitHub 밖에서 발화) | 정상 | 알고 대응 |
| 텔레그램 장애 | 무관 | 무관 | 정상 | P0는 ntfy로 도달(B4) |
| 데이터소스 스로틀(F5) | 해당 종목 진입 보류 | 파수꾼은 브로커 시세 사용(quote 나이 검증) | 정상 | 영향 최소 |

**정확한 주장(2차 검토로 정정)**: 위 표가 보장하는 것은 "단일 **인프라** 장애가
**직접** 손절 불능으로 이어지지 않는다"까지다. **파수꾼↔브로커 경계**에서는
여전히 깨질 수 있다 — 실측 가능한 반증 7종과 방어(2차 검토 §5, 전부 Phase B에 편입):
① 브로커 토큰 만료(주문만 401) → **장전 preflight + auth 실패=P0** ② 주문 UNKNOWN
후 재주문 → 초과매도 → **UNKNOWN lock + open orders 대사 후 잔여만** ③ 부분체결
수량 불일치 → **브로커 포지션이 source of truth** ④ 브로커 시세 지연 → **quote
나이 >10~30초면 손절 판단 금지** ⑤ feed 낡음에 최신 트레일 stop 미전달 →
**파수꾼 내부에도 stop 래칫 유지, 마지막 확정 stop은 계속 집행** ⑥ 파수꾼+GitHub
동시 사망 → **B0 브로커 stop이 유일 방어** ⑦ 액면분할/기업행위 → **수량 불일치
시 신규 주문 금지 + 수동 리뷰**.

## 6. 실거래 도입 단계 (2차 검토 §10 채택 — "처음부터 1% 리스크 금지")

| 단계 | 기간/조건 | 리스크·규모 | 통과 기준 |
|---|---|---|---|
| **Stage 0 그림자** | 2주+ | 주문 0건 — 파수꾼이 브로커 **조회만** live | auth 실패 0 · quote stale 원인 파악 · UNKNOWN 시뮬 통과 |
| **Stage 1 마이크로** | 2~4주 or 주문 10~20건 | 종목당 **0.1~0.25%** · 동시 1~2종목 · 하루 1건 · 한 시장만 | UNKNOWN 미해결 0 · 부분체결 reconcile 실패 0 · 손절 주문 실패 0 |
| **Stage 2 제한** | Stage 1 무사고 후 | 0.25~0.5% · 3~5종목 | 원장·하트비트 안정 + B0 확인 |
| **Stage 3 정상 후보** | 주문 50~100건 무사고 + **장애 주입 테스트 통과** | 1% 후보 | P0 누락 0 |

**장애 주입 테스트(발췌)**: GitHub 1시간 중단 가정 · 파수꾼 kill · 토큰 만료 ·
주문 timeout(UNKNOWN) · 부분체결 · feed 30분 stale · 중복 dispatch · 텔레그램 차단
→ 각각 기대 동작(진입 금지/재시도/reconcile/P0 도달)이 실제로 나오는지 확인.
