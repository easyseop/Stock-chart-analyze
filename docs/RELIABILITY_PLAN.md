# 신뢰성 종합 분석 — "깃액션이 자꾸 죽는" 문제와 실거래 무리스크 운영안

> 2026-07-08 작성. 2주 운영(사건 16건)의 실측을 근거로 한 결정 문서.
> 결론 요약: **고장 나는 것은 GitHub이 아니라 '무료 크론의 정시성'이다.
> 정시성이 필요한 경로(가격→매매→손절)를 계층별로 분리해, 각 계층에
> 맞는 인프라를 배정하면 실거래에서도 "장애 = 손실"이 아니라
> "장애 = 신규 진입 공백(기회비용)"으로 격하된다.** 이것이 목표 상태다.

## 1. 진단 — "죽는다"의 실체 (전부 실측)

| # | 고장 모드 | 빈도 | 실측 증거 | 매매 영향 |
|---|---|---|---|---|
| F1 | **GitHub 크론 드랍** (best-effort) | **상시** | 7/7 하루 schedule 7/60회 = **드랍 88%**. 7/6 밤 9시간 전멸 | 빌드 지연 → 가격·매매 15분→최대 수시간 지연 |
| F2 | 플랫폼 이벤트 동결 (push·schedule 전면) | 드묾 | 7/7 아침 3시간(B6). dispatch만 생존 | F1과 동일, 더 김 |
| F3 | Pages 배포 실패 | 가끔 | A4·B2, 재시도로 회복 | **없음** (표시만 지연 — 매매는 빌드 안에서 완결) |
| F4 | **자초한 정체** — 전체 재렌더 연속 투입 | 1회(7/7) | #52~54 재렌더 3연속 → 가격 빌드 큐 밀림 33분+ | 가격·매매 지연 (운영 실수) |
| F5 | **종목 단위 무음 정지** — 데이터소스 스로틀 | 가끔 | TSLA 6시간 419.77 동결(타 종목은 센트 단위 일치) | 그 종목만 낡은 가격 — 경고 없음이 문제 |
| F6 | 캐시 휘발(계좌·수집분) | 과거 | A1 | **해소** — state 브랜치 백업(7/7 가동) |

**근본 원인 한 줄**: 무료 GitHub 크론은 "정시 실행을 보장하지 않는 것이 계약 조건"인데,
우리 시스템의 심장(가격 갱신→자동매매)이 그 정시성에 얹혀 있다.

**이미 작동 중인 방어** (이번 주에 실증됨):
cron-job.org 외부 킥(오늘 시스템을 실질 가동한 주력) · 워치독 자가치유 ·
오프피크 크론 · guard 공회전 방지 · state 브랜치 계좌 백업 · 전 실패 경로 텔레그램.
→ **덕분에 "계좌 손상"은 지금까지 0건.** 남은 문제는 "지연"이지 "손실"이 아니다.

## 2. 설계 원칙 — 정시성 요구로 계층을 나눈다

같은 시스템 안에 정시성 요구가 전혀 다른 세 가지 일이 섞여 있다. 분리가 답이다.

| 계층 | 일 | 정시성 요구 | 맞는 인프라 |
|---|---|---|---|
| L1 분석·렌더 | 5,400종목 스캔, 900MB 페이지 | 낮음(수십 분 늦어도 무해) | GitHub Actions (무료 무제한, 지금처럼) |
| L2 **가격→매매 스텝** | 보유·후보 시세 + 자동매매 1스텝 + 피드 | **중간(15분 보장)** | GitHub Actions 실행 + **보장된 외부 발사·검증** |
| L3 **손절 집행** (실거래) | 보유 종목 손절선 감시·매도 | **높음(초 단위, 항상)** | **상주 프로세스** — GitHub으론 불가능, 별도 호스트 |

핵심 통찰: L2를 L1에서 떼어내면(빠른 모드) 오늘 같은 렌더 정체(F4)가 매매를 못 막고,
L3를 GitHub 밖에 두면(파수꾼 — 이미 dry-run 완성) **GitHub 전면 장애조차 손실로
이어지지 않는다.** 이 두 분리가 전체 계획의 뼈대다.

## 3. 로드맵 — 3단계 (비용 0~5$/월)

### Phase A — 지금(모의 단계) 바로: "지연"을 구조적으로 줄인다

| # | 항목 | 해결하는 고장 | 작업 |
|---|---|---|---|
| A1 | **빠른 모드(fast) 분리** — 보유·대기·후보 시세 + autopaper + 피드만 갱신(~3분), 페이지 렌더·배포 생략 | F4 (렌더가 매매를 막는 구조) | 코드(클로드) |
| A2 | **Cloudflare Worker 크론** — 15분마다 fast 발사 + "런이 진짜 생겼나" 검증 + 미생성 시 재시도. CF 크론은 best-effort가 아니라 **보장 실행**(무료 10만 요청/일, 우리 사용 ~200/일) | F1·F2 (발사 신뢰성) | Worker 코드(클로드) + CF 계정 연결(사용자 ~20분) |
| A3 | **종목별 신선도 스탬프 + 무음 정지 경보** — 데이터 나이가 임계 초과한 보유/추천 종목은 강제 재수집, 반복 실패 시 텔레그램 | F5 (TSLA류 무음 동결) | 코드(클로드) |
| A4 | **운영 규율의 코드화** — 전체 재렌더(BUILD_SHA 변경)는 장중이면 다음 장외로 지연 | F4 재발 방지 | 코드(클로드) |

Phase A 후 상태: 발사는 CF가 보장, 매매 경로는 3분짜리 경량이라 밀릴 일이 없고,
종목 동결은 자동 감지·회복. **cron-job.org는 2차 백업으로 유지**(이중 발사는 guard가 걸러냄).

### Phase B — 실거래 결정 시: "장애 ≠ 손실" 보장

| # | 항목 | 근거 |
|---|---|---|
| B1 | **파수꾼(sentinel) 상주 가동** — Oracle Cloud 무료 티어 또는 $5 VPS. 손절 전담(매수 경로 없음 — 코드에 이미 grep 테스트로 보장) | L3 분리 — STRATEGY 5.5.1, 코드 완성·dry-run 검증 끝 |
| B2 | **주문 원장 + 부분체결 reconcile + 포지션 정체성 멱등키** | SRE 재검토 지적 — 스펙 주석으로 이미 고정(sentinel.py) |
| B3 | **concurrency 전용 그룹 + state lock** — 같은 주문 이중 발사 차단 | 현재 pages 그룹 직렬화 → 전용 승격 |
| B4 | **P0 경보 ntfy 이중화** — 텔레그램 죽어도 매매정지·위반·파수꾼 사망은 도달 | 남은 유일한 경보 단일점 |
| B5 | **CF Worker가 파수꾼 하트비트 감시** (감시의 감시) — 파수꾼 무응답 N분 → P0 | 데드맨 스위치를 GitHub 밖에 |

### Phase C — 실거래 안정화 후

- 브로커 실보유 ↔ 내부 상태 자동 대사(일 1회) · 슬리피지 계측 리포트
- (선택) 전략·계좌 비공개화 — 공개 러너 + 비공개 브레인 분리

## 4. "리스크 없이"의 정확한 의미 — 실거래 장애 매트릭스

Phase A+B 완료 상태에서 각 장애가 돈에 미치는 영향:

| 장애 시나리오 | 신규 진입 | **보유 손절** | 계좌 기록 | 결론 |
|---|---|---|---|---|
| GitHub 크론 드랍(F1) | CF가 발사 — 정상 | 파수꾼 정상 | 정상 | 영향 없음 |
| GitHub Actions 전면 장애(F2) | **공백** (기회비용) | **파수꾼이 계속 집행** ✅ | state 브랜치 보존 | **손실 없음** — 새로 못 살 뿐 |
| CF Worker 장애 | GitHub 크론+cron-job 백업 발사 | 파수꾼 무관 | 정상 | 지연만 |
| 파수꾼 호스트 사망 | 무관 | ⚠️ 15분 폴링(GitHub 경로)으로 강등 + **P0 경보 즉시**(B5) | 정상 | 알고 대응 — 이때만 사람 개입 |
| 텔레그램 장애 | 무관 | 무관 | 정상 | P0는 ntfy로 도달(B4) |
| 데이터소스 스로틀(F5) | 해당 종목 진입 보류 | 파수꾼은 브로커 시세 사용 — 무관 | 정상 | 영향 최소 |

**핵심 성질**: 어떤 단일 장애에서도 "손절 불능"이 발생하지 않는다.
손절 경로(파수꾼)가 GitHub·CF·텔레그램 어느 것에도 의존하지 않기 때문.
최악의 조합(GitHub+CF 동시 장애)에서도 결과는 "신규 진입 공백"이지 손실이 아니다.
